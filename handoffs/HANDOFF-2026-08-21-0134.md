## Work Completed

### Signal graph rewrite — `8f19a9d`

`packages/client/src/signal.ts`, 53 lines → a real graph. Own implementation taking
alien-signals' techniques.

- Doubly-linked dependency edges: one `Link` sits in the dependency's subscriber list and
  the subscriber's dependency list at once. Unlinking is four pointer writes, no hashing,
  no allocation; a re-run walks its existing links and reuses them.
- Bitflag node status on one integer: `MUTABLE`, `WATCHING`, `DIRTY`, `PENDING`, `QUEUED`,
  `TRACKED`.
- Push-pull: a write marks direct subscribers `DIRTY` and everything downstream `PENDING`,
  then `checkDirty` answers the pending question once at flush, stopping at the first
  computed that actually moved.
- `subscribe` stays narrow — one dependency, no tracking, **does not run on creation**.
  `effect` is the auto-tracking door.
- 18 tests: diamonds, dynamic dependency pruning, cancelling writes, cold computeds,
  reentrant flush.

### Derived values, IR 2.2.0 — `e031df5`, `d47c956`

`E_DERIVED_SIGNAL_UNSUPPORTED` removed. `{n() * 2}` compiles.

- New `derived` table on the IR: an expression tree (`ref`/`lit`/`un`/`bin`) over a closed
  operator set, evaluated by the server to render and by the client inside a `computed`.
  Both evaluators are one switch; a `ref` to a missing binding reads `null`.
- Ownership follows the reads: an expression reaching a signal is the client's and gets a
  wiring entry; one over props alone is the server's and rides in the delta.
- `packages/ir/src/derived.ts`, `packages/client/src/derived.ts`, compiler `derivedExpr`.
- New `derived` bench scenario, added to conformance defaults.

### Component composition, IR 2.3.0 — `51c4b68`, `ffa07d8`, `806cd2c`, `59fa9a5`

- `component` hole kind: a sealed child template plus `props`, mapping child prop name to
  the parent binding that supplies it. Nothing is inlined — one child used five times is
  one sealed template used five times.
- An instance occupies exactly one element position, so a component must render a single
  root element. Marker collection stops at the boundary.
- Client adopts an instance as its own template with `origin: 'element'`; the parent's
  signals arrive renamed to the child's prop names.
- A delta addresses an instance by name (`c0.label`) the way it addresses a row by index.
- `composed` bench scenario, added to conformance defaults.

### Property bindings — `e356391`

The `prop` wiring op the IR has carried since 2.0.0 is now honoured. The server renders the
attribute; the client writes the property behind it. Table keyed by tag: `value`/`checked`/
`indeterminate` on `input`, `value` on `textarea`/`select`, `selected` on `option`, `value`
on `progress`.

### Cross-module composition — `1c0ebf3`

`compileFiles` parses every file, reads exports and rendered tags, resolves tags to files,
sorts by dependency, compiles children first, and returns modules in the caller's order. A
cross-module child arrives already sealed. Two modules rendering each other are
`E_COMPONENT_CYCLE` naming the path.

### Route contagion, IR 2.4.0 — `6b3c623`, `7064bed`, `fc8c4a5`

A private child inside a non-private parent is **isolated**: the hole is marked, the parent
does not render it, and `splitAtSlots` cuts there so the kernel composes the two at stream
time from two cache entries. Decision uses the parent's **own** class, so it is
order-independent. Only `private` isolates.

`ROADMAP.md` added: unbuilt runtime work in dependency order, then a documentation site
with a live playground and a demo site with one station per capability.

## Corrections Made Mid-Session — Read This First

These are the reason to read the diffs rather than trust the commit titles.

### Blind effect union was wrong, and shipped for two commits

`51c4b68` unioned a child's reads into its caller's unconditionally, and its spec text and
test asserted that a private child makes its caller private. `spec/compiler/effects.md`
says the opposite: **a private fragment should not make its route private.** Corrected in
`6b3c623`; the test was replaced rather than extended.

**Lesson**: containment is not an exception inside the union, it is a change of shape. The
child stops being inlined and becomes its own cache unit.

### The signal graph rewrite made its own referee slower

| Engine   | `Set` of subscribers | linked graph |
| -------- | -------------------- | ------------ |
| Chromium | 0.28 µs              | 0.31 µs      |
| Firefox  | 1.7 µs               | 1.7 µs       |
| WebKit   | 0.72 µs              | 0.74 µs      |

Measured back to back on one machine on `isolated-dom-update`. The old code went straight
from `set` to the subscriber call; the new one pushes through propagate, a queue and a
flush. Recorded in `spec/FINDINGS.md` as a cost, not a win. **Do not re-report this as a
performance improvement.**

What it bought: a write through a computed is **not separable** from a direct write in any
of the three engines — the harness refused all three comparisons rather than report a
difference inside its own noise.

### Instance targets must not be folded into the parent's table

First attempt merged a child's targets under the parent's binding names so
`adopted.write('tone', v)` would reach inside. That makes one changed value two writes and
failed the "one write per changed path" conformance check. Removed; the delta addresses the
instance by name instead.

### Deltas were carrying values nothing could write

Pre-existing, surfaced by the `derived` scenario. A prop appearing only inside an
expression has no hole, so the client skipped it — one write for two paths. Deltas now
carry only what the template can address.

### A scenario transition that moved a signal was a category error

Both the `derived` and `composed` scenarios initially moved a signal in
`transitionValues`, asking the server to re-render state the client owns. Fixed by moving a
prop. **A delta is the server's update; a signal is the client's state.**

### Ownership has to cross the component boundary explicitly

A parent signal passed as a prop is client-owned on the other side, but the child declared
it as an ordinary prop and cannot know. Without carrying that across, the server sent
`c0.d0` for a value the client was already recomputing. `changesFor` now takes a
`fromSignal` set.

## Key Decisions

- **`subscribe` does not run on creation.** Adoption binds to DOM the server already
  filled; a watcher that ran would rewrite it. This is why `subscribe` and `effect` exist
  separately rather than one being sugar for the other.
- **A component is a projection, never an inlined copy.** Content-addressed reuse, one
  template per child regardless of use-site count.
- **Single root element for a component.** Trade-off: rules out multi-root components.
  Reason: an instance must occupy one element position or every sibling path becomes
  dependent on what the child rendered.
- **Prop wiring is decided for the whole build.** An export another module renders is
  composable and gets wiring; one nobody renders does not. Consequence: **a fragment's
  version moves the first time somebody composes it.** Deemed correct — a composable
  template is not the same template — and documented rather than hidden.
- **Only `private` isolates.** A shared child inside a static parent still composes; the
  cost there is a wider cache key, not a correctness problem, and cutting on it would turn
  every cookie read into a separate request.
- **Isolation uses the parent's own class, not its composed one**, so the answer cannot
  depend on which child is examined first.
- **Three IR minors rather than one.** 2.2.0 derived, 2.3.0 components, 2.4.0 isolated. The
  last two are recorded in `spec/VERSIONING.md` as additive changes that are **not**
  silently forward-compatible: an older reader meeting an unknown hole kind, or ignoring
  `isolated`, would render private bytes into a shared entry. Version negotiation drops to
  `html`, which is the protection that matters.
- **`fragment()` now returns `JSX.Element`** so the checker accepts `<Widget/>`. The value
  is never called at runtime; the compiler resolves tags statically.

## Next Steps

**The ordering in `ROADMAP.md` is wrong on one point and the design is right.** The roadmap
puts runtime cache key resolution first; the design's build order puts kernel and ports
(phase 2) before the plan layer (phase 4). This project built phase 4's front half —
effect inference, cache classes, contagion — on top of a kernel that does not exist, which
is exactly why `requiresTtl` has nothing to contradict.

1. **Phase 2: the kernel.** Request state machine, two-phase envelope lifecycle,
   103 Early Hints, port interfaces. This is the floor everything else stands on.
2. Then runtime cache key resolution, which now has a request to hang off.
3. Then cache policy declarations validated against inferred effects.
4. The documentation site and its playground depend on none of the above and can start in
   parallel at any time — the compiler already has no Node dependency in its hot path,
   only `compileFiles` needs a virtual file system.
