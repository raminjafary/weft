Landscape survey & architecture proposal

Weft & Warp

Every meta-framework decides what to render. None of them lets you declare when each byte arrives, in what form, or on which machine. That is the unclaimed territory — and it is where a new TypeScript fullstack framework can be genuinely, defensibly first.

August 2026 Greenfield · no RSC Survey → gap analysis → design

Superseded in places

This document is the design as written, before any of it was built. It has since been implemented and measured, and four of its claims are wrong: TTFB is not the gate it is described as here, the data wire form has been cut, escape elision is not a throughput lever, and incremental declarative shadow DOM is not the risk it is called. The most instructive data point is not a framework

It is a large production web app, and the reason to look at it is purely that someone published a full teardown of its delivery layer. The app happens to be chatgpt.com; nothing about the subject matter is relevant here, and nothing in this proposal involves machine learning. What is relevant is that it is a React 19 + React Router 7 streaming-SSR app on Vite — a completely ordinary web stack — hitting 50–65 ms TTFB with an 84 KB compressed document across 354 routes, where everything that makes it fast is not in the framework:

  • A boot sequence organized around one named milestone — "can you type yet?" — with 100+ chunks and exactly 14 modulepreloaded.
  • Route-specific stylesheets, split by hand: root, conversation, code-block.css, cot-message.css.
  • Per-user prefetch decisions computed on the server and inlined: shouldPrefetchModels, shouldPrefetchHistory.
  • 556 feature gates evaluated server-side and inlined into the HTML to avoid a client round-trip — with gate names hashed so the roadmap does not leak.
  • Flags that control the loading strategy itself, not just which UI renders.

Every serious company rebuilds this same layer from scratch. That is the definition of a missing framework primitive.

Part two

Fourteen gaps that are actually open

Scheduling

The critical path is not a program

Frameworks own what renders and how it bundles. No framework lets you declare arrival order, priority, and conditions as a checkable artifact.

ChatGPT's deferStartupImportsUntilComposerTTFI is this concept, hand-rolled, as a boolean.

Flags

Flags are runtime ifs or build explosions

Today a flag either ships both branches to the client, or forces you to prerender every permutation. There is no middle: a flag as a typed axis that partitions the module graph, enters the cache key, and resolves once at the edge.

Granularity

One protocol, five jobs — nobody has it

Initial shell, out-of-order holes, later navigations, post-load fragment refreshes, and mutation responses are five different mechanisms in every framework. They are the same problem: DOM patches addressed to slots.

Cacheability

Nothing tracks what a render read

Cookies wreck caching because cache keys are hand-written and drift. If the compiler knew which request-scoped values a fragment touched, the key would be derived — and a cacheable fragment reading identity would be a build error.

Render authority

The client can name components

Server functions and RSC-style payloads let the client reference server code. Mobile SDUI solved this years ago with registered capability allowlists and signed layouts. The web never adopted it.

Wire form

The form a UI travels in is frozen at build time

Every framework picks one shape and commits: HTML, or a flight payload, or JS chunks. Nothing lets the runtime choose between one inlined bundle and code-split chunks per request, based on what the client already holds and how bad its network is.

Render locus

Rendering blocks the thread that owns the stream

Server rendering runs on the request path everywhere. One heavy fragment stalls every other slot's flush. No framework treats where a render executes — this thread, a worker pool, a separate isolate — as a per-slot declaration.

Data currency

Fresh data always means a changed view

Fetching implies committing, everywhere. Nothing lets you hold a fresh, fully-resolved dataset uncommitted and addressable, then flip several slots to it atomically — so background revalidation always risks disturbing the user.

Server recompute

Surgical updates exist, but only with a stateful server

Phoenix LiveView genuinely solved minimal server-side recompute and minimal wire diffs. It needs a stateful process per connection to do it — so no serverless, no CDN, no sharing a diff between users.

Styles

Nobody streams CSS, and FOUC is the reason

Flash-of-unstyled-content in streaming SSR is an open issue across Qwik, Next, Nuxt, TanStack Start, and Quasar. @layer has made arrival order irrelevant since 2022 and no framework uses it to make CSS streamable. Critical extraction still guesses at the fold.

Load granularity

An island is both reactive scope and code unit

Signals made updates fine-grained everywhere and left loading coarse. One interactive button drags its whole module along, and most handlers only need to tell the server something — which requires no component code at all.

Variants

Multi-tenancy is a linear chain or a runtime config

Nuxt Layers give a build-time override chain; SaaS multi-tenancy is runtime config. Nothing is typed, multi-dimensional, and wired into the cache key — which is why cross-tenant cache leakage keeps happening.

Envelope timing

Late cookies and status codes are forbidden, not solved

Once streaming starts the response envelope is sealed, so every framework simply bans setting cookies during render and documents the restriction. Nobody makes the constraint granular, type-enforced, or measurable — and nobody uses 103 Early Hints to keep the envelope open while preloads fly.

Feedback loop

Production data never reaches the build

Native toolchains have fed production profiles back into compilation for two decades. On the web the loop runs one way: build plugins push source maps to monitoring. Guess.js tried the reverse in 2018 for prefetching alone, and is dormant.

Part three

The proposal

Make the framework's central artifact neither the component tree nor the route table, but the delivery plan — a declarative, compiler-derived, flag-parameterized description of what bytes arrive when, over one multiplexed stream, with per-fragment rendering strategies and cache keys derived from what the render actually read.

Two names, because they do two jobs. Warp is the protocol — the long-lived threads held under tension for the whole session. Weft is the framework that weaves fragments across it. The metaphor is load-bearing, not decorative: the warp persists, the weft arrives incrementally, and the fabric is legible before it is finished.

Why this is the right bet

Because the rendering layer is genuinely finished. Streaming, islands, and signals are solved problems with multiple good implementations — Marko 6 in particular has had automatic partial hydration and out-of-order streaming for years, and it has near-zero mindshare, which tells you that better rendering does not win. What no one has commoditized is the delivery layer that every large team hand-builds on top. Own that, and you inherit the rest by being a good citizen of Vite, Nitro-style adapters, and TC39 signals.

Architecture

A microkernel that only executes plans

The kernel does four things and nothing else: own the request lifecycle as a state machine, resolve a plan, execute it against ports, and own the stream. Target under 8 KB server-side. Every capability people normally call a "framework feature" — ISR, SWR, PPR, edge caching, cookie handling — becomes a port implementation, typically under 50 lines.

  • RenderPortTurns a fragment into bytes. stream, buffered, isr, swr, static, client-only, remote are all just implementations.
  • StorePortContent-addressed cache keyed by the derived effect signature. Memory, Redis, KV, R2, filesystem.
  • FlagPortFlag resolution. OpenFeature, Statsig, LaunchDarkly, or a local file. Resolved once per request, inlined into the stream.
  • SessionPortCookies, tokens, identity. Swappable without touching caching, because caching does not depend on it.
  • TransportPortHow Warp frames travel: HTTP chunked, H2/H3 stream, SSE, WebTransport. Degrades to plain request/response.
  • SchedulerPortDecides slot ordering and priority at runtime. The plan is data, so the scheduler can reorder to fill the pipe fastest-first.
  • AssetPortOwns the chunk graph and emits modulepreload / link rel=preload in the flush that needs them.
  • TelemetryPortEmits the plan's own named milestones as RUM marks, so the boot budget is measured, not assumed.

The guarantee this buys

"Set a cookie without worrying" is not a slogan here; it is a consequence. Because the cache key comes from the effect signature rather than from the session port, swapping cookie backends cannot invalidate caching behavior, and reading a cookie in the wrong place is a compile error rather than a silent cache bypass.

Boundaries

What is replaceable, and what deliberately is not

"Everything is swappable" is a claim worth distrusting. A microkernel that lets you replace its own scheduling contract is not a microkernel, it is a pile of modules with a marketing page. The honest shape of this design is a small set of fixed invariants surrounded by an almost entirely replaceable periphery — and the invariants are what make the guarantees possible.

The invariants still have local escape hatches

Fixed does not mean inescapable. It means you cannot redefine it globally and keep the guarantee. Where an invariant does not fit, you opt out in one place, loudly:

  • ctx.raw() — leave effect tracking for one fragment. It becomes uncacheable and private, and weft why reports it. Local, not viral.
  • .executor('client') — leave server rendering for one slot.
  • Turn off Warp — plain request and response, forms fall back to html.
  • Ship no JavaScript at all — server-rendered HTML with declarative-shadow-DOM holes.
  • Mount the kernel inside Hono, Elysia, or Express — it takes a Request and returns a Response, nothing more.

Extensible and unopinionated are different things. This design is extremely extensible at the periphery and deeply opinionated at the core — and the opinions are not preferences, they are the preconditions. You cannot promise that setting a cookie will not wreck your caching unless something is tracking the reads.

Core mechanism

Effect-tracked rendering

This is the single strongest idea in the design, and the one with no prior art in a frontend framework. Every request-scoped read goes through a typed context, and every read taints the fragment:

fragment · reads are inferred, never hand-written
// weft infers: reads = [flag:new-cart, cookie:currency]
// derived key  = h(cart-summary@a91f, new-cart=on, currency=IQD)
// derived class = SHARED  (no identity read → CDN-cacheable)

export default fragment(async (ctx) => {
  const layout   = await ctx.flag(newCart)      // taints: flag
  const currency = ctx.cookie('currency')      // taints: cookie
  const lines    = await cart.summary(currency)
  return layout === 'v2' ? <CartV2 {...lines} /> : <CartV1 {...lines} />
})

From that inference the compiler derives four things automatically:

  • The cache key. A hash of fragment identity, content version, and the sorted set of tainting reads with their resolved values. Never written by hand, therefore never stale.
  • The cache class. Reads nothing → static, hoisted to CDN at build. Reads only flags → one variant per reachable flag combination. Reads ctx.user() → private, never shared, full stop.
  • Build errors. A fragment declared cache: 'public' that reads an identity-tainted value fails the build. So does a slot marked server-only whose code is reachable from a client chunk.
  • The flag axes. Each flag becomes a typed dimension of the plan, and the compiler reports which permutations are actually reachable — turning the combinatorial explosion into a small, enumerable set.

Think of it as Vary: promoted to a type system. And because a flag is now a graph partition rather than a runtime branch, only the resolved branch's chunks are reachable from the client — the losing variant's code is never downloaded, which no current flag SDK achieves.

The hard constraint

Envelope effects: what happens when a late slot wants to set a cookie

This is the genuine unsolved problem in streaming SSR, and it is worth being precise: it is not a framework bug, it is HTTP. Status line and headers precede the body. The moment the first body byte is flushed, the response envelope is sealed. A slot that resolves at 300 ms and wants to Set-Cookie, return 302, or set Cache-Control has missed its window permanently.

How everyone currently answers it

They don't — they forbid it, and document the restriction. Next.js states plainly that setting cookies is not supported during Server Component rendering, precisely because streaming requires headers before rendering completes; the guidance is to use a Server Function, a Route Handler, or middleware instead. SvelteKit requires setHeaders to be called before resolve, and throws if the same header is set twice. Remix and React Router sidestep it by running loaders to completion before rendering starts, which is correct but gives up early flush. Every framework picks a side of the tradeoff and writes it in the docs.

So the goal is not to defeat physics. It is to shrink what the constraint actually blocks, make the bug impossible to write, give the late cases a real second channel, and name exactly what is irreducibly lost.

Layer zero — decouple "flush preloads" from "commit the envelope"

The reason everyone feels pressure to flush early is to get preload hints out. HTTP already separates those two things and almost nobody uses it. 103 Early Hints — RFC 8297, implemented in Chrome, Safari, and at the Cloudflare edge — sits between the request and the final response. Send 103 with Link preloads for the shell's CSS, fonts, and critical chunks at effectively zero milliseconds; the browser starts fetching immediately; the envelope stays open. Then resolve the envelope, then send the real 200 or 302 with its Set-Cookie headers, then stream the body.

This reframes the whole tradeoff. Most of the perceived benefit of an early flush is subresource discovery, and Early Hints delivers that without sealing anything. The caveat is real and should be stated: it is HTTP/2 and HTTP/3 only, so an HTTP/1.1 client simply waits for phase A. Firefox has an implementation not enabled by default.

Layer one — envelope effects are declared, and the bug becomes unrepresentable

The read-tracking machinery already exists; this is its mirror image. Every write to the response envelope — cookies, status, Location, Cache-Control, Vary — is an envelope effect, and the lifecycle splits in two:

two phases, two context types, one enforced boundary
export default fragment({

  // phase A — before any byte leaves. envelope is open.
  // cheap by nature: session, locale, flag bucket, auth.
  envelope(ctx) {
    const s = ctx.session.rotateIfStale()      // Set-Cookie, HttpOnly, fine
    if (!s) return ctx.redirect('/login')      // real 302
  },

  // phase B — streams. ctx here is a DIFFERENT TYPE with no
  // envelope methods at all, so the mistake cannot be written.
  render(ctx) { ... }
})

Three consequences. The compiler knows exactly which slots have envelope work and therefore gate the first flush, and it names them at build time with a budget — instead of you discovering a dropped cookie in production. Envelope work is cheap by nature: session checks, locale detection, flag bucketing, auth guards, not expensive data fetches. And in this architecture flags, session validity, and locale are already resolved in the gateway tier before rendering begins, so phase A usually collapses to near-nothing.

One common need disappears entirely: Vary and Cache-Control are derived from the static effect signature, not discovered at runtime. The single most frequent reason to want a late header is a non-issue by construction.

Layer two — defer the envelope to the next request on the connection

This one is available to us and to nobody else, and it is the part I am most pleased with. Warp is a long-lived connection, so an envelope effect that resolves too late for this response can be queued and attached to the headers of the next request on that connection — which for an interactive app is milliseconds away, and which is a real HTTP response, so HttpOnly and Secure work normally.

The type system decides eligibility rather than the developer: ctx.envelope.deferrable(...) is permitted in phase B, ctx.envelope.required(...) is only callable in phase A. Deferrable means idempotent and refreshable — token rotation, a preference cookie, a last-seen timestamp. Recording consent is not deferrable, and the compiler will not let you pretend it is. The honest loss case: if there is no next request, a deferred effect is dropped, which is exactly why only idempotent effects qualify.

Layer three — in-band frames for what remains

Once headers are committed, Warp can still carry envelope-ish intent in the body: a REDIRECT frame the client acts on, degrading to an inline script or meta refresh with no JavaScript; a COOKIE frame for non-HttpOnly values. These handle the user-facing cases and nothing more.

What is irreducibly lost, stated plainly

After the envelope is sealed you cannot retroactively obtain: a real status code — which matters for crawlers, CDN caching, and monitoring; an HttpOnly or Secure cookie in-band; Cache-Control or Vary, because the CDN has already decided; or a redirect a crawler will follow. Anything requiring those must be in phase A, and the compiler's job is to force it there rather than let you find out later. HTTP trailers look like an escape and are not one — browsers do not apply them to these semantics.

Layer four — the structural fix, which is where most of the value is

Nearly every real instance of "I need to set a cookie mid-stream" is actually "I discovered too late that I needed a guard." So make guards a plan-level declaration that runs in phase A by construction:

the 90% case, moved to where it belongs
guard(session.required, { redirect: '/login' })   // phase A, real 302
guard(flags.resolved)                                // edge, before render
guard(locale.negotiated)                             // edge, sets cookie if needed

slot('feed').stream({ prio: 1 })                    // envelope: none, provably

And the profile closes the loop: it reports which routes actually incur late envelope effects in production, so the ones worth restructuring are identified from data rather than guessed at. The constraint stops being a trap and becomes a measured, named, budgeted line item — which is the most that can honestly be claimed, because the underlying limit is HTTP itself.

Principle

Everything opt-in, everything opt-out, no cliffs

The failure mode to design against is not slowness — it is the cliff. Opting out of a framework's fast path today usually drops you two tiers, not one, and it does so at a granularity you did not choose.

The canonical cliff

Next.js documents it plainly: in a non-PPR route, a single cookies(), headers(), or searchParams call anywhere in the route tree opts the entire route out of static rendering. A personalised banner reading one cookie makes a whole page dynamic. Partial Prerendering fixes this — but only if every dynamic call is manually placed inside a Suspense boundary, which means auditing the tree and remembering forever.

Our answer is not a better default. It is that the boundary is derived. Effect tracking already knows exactly which slot read the cookie, so the dynamic region is that slot and nothing else — no audit, no annotation, nothing to forget, and no route-level contagion by construction. The unit of opt-out is the slot, never the route.

CSR and SSR are the same source, chosen per slot

Because a fragment is a function of typed context reads and templates compile to a wiring table, the compiler emits both entry points from one source: a server entry that writes bytes, and a client entry that writes DOM. There is no 'use client' split, no duplicated components, no parallel implementations. The plan picks per slot, and the whole spectrum is expressible — a fully server-rendered page, a fully client-rendered app, or any mix — without changing a line of component code.

And the boundary is enforced rather than trusted: a fragment that reads a server-only effect cannot compile to a client entry point, and attempting it is a build error naming the offending read. That is the isomorphic-first direction the ecosystem is already converging on, with the boundary policed by effects instead of by directives a reviewer has to catch.

Isolation

Server code must be unable to reach the client bundle

SvelteKit has the best existing answer and it is worth quoting its reasoning exactly: even when public-facing code imports only the non-secret exports, the secret code can still end up in the JavaScript the browser downloads, so the import chain itself is considered unsafe. That is the correct standard — reject on the chain, not on what appears to be used. The mechanism there is a convention: a .server.js suffix or a $lib/server directory.

A convention is a good floor and it has two holes. It only protects modules someone remembered to name correctly, and it says nothing about data leaking — a module can be perfectly server-resident and still serialise a password hash into the page. Both need closing, and both close with machinery this design already has.

Residency is derived, exactly like effects

Every module gets an inferred residency: server, client, or shared. A module that touches a port, a node: builtin, ctx.raw(), or a secret is server. A module reachable from an island's reactive subtree, or that touches window or document, is client. Everything else is shared. Residency propagates transitively along imports, and a module forced to be both is a build error printing the full chain that caused it:

No directives — they are a workaround for missing inference

'use client' and 'use server' exist because a bundler that cannot see effects has no way to derive residency, so it has to be told. We can derive it, so asking would be redundant — and string directives are a bad mechanism on their own terms:

  • Invisible to the type system. Nothing checks them. 'use cleint' is a no-op that silently changes your application's architecture.
  • Not navigable. No go-to-definition, no find-references, no rename. A string literal carrying load-bearing semantics that no tool understands.
  • Position-sensitive. Valid only at the top of a file, above imports, which makes them fragile under refactoring and formatting.

So there are no directives. Where you genuinely want to state intent rather than rely on inference, there are two mechanisms that are ordinary code:

two non-directive ways to be explicit
// 1. path convention — SvelteKit's approach, and it is a good one.
//    app/lib/server/**  is server-resident by configuration, not by string.

// 2. an ordinary import. importing this module IS the assertion,
//    because the module is server-resident by definition.
import 'weft/server-only'
//     ^ a real module. type-checked, navigable, renameable.
//       reached from a client chunk → a normal resolution error
//       with the import chain, not a silently ignored comment.

import type { User } from './types'   // types never reach any bundle

In practice you will reach for neither. Touching a port, a node: builtin, or env() already makes a module server-resident, and that covers essentially every real case.

Secrets are a type that cannot cross

Default-deny, which is the inverse of the prefix conventions everyone forgets. env('SESSION_SECRET') returns an opaque Secret<string> — no toString, no toJSON, and a compiler rule that a Secret may never appear in a serialisable position. env.public('API_URL') is the explicit opt-in for anything allowed clientward. Forgetting a prefix leaks silently; forgetting .public() is a type error.

The schema that makes the data and delta wire forms possible is the same schema that whitelists what may leave the server. The performance feature and the security feature are one feature.

The wire is a declared schema, not an inference

This is the part no framework does well, and here it costs nothing extra. The data form already requires a schema — the client projects values through a resident template, so the server must know the shape it is sending. Make that schema the serialisation allowlist:

over-fetching becomes harmless
export const CartLines = fragment({
  // the ONLY fields that may cross to the client for this fragment.
  // the serialiser emits nothing else, ever.
  wire: v.object({
    lines: v.array(v.object({ sku: v.string(), price: v.number() }))
  }),

  async render(ctx) {
    const user = await db.user(ctx.user())   // full record, hash and all
    return <Lines lines={user.cart.lines} />   // only sku + price leave
  }
})

Module-level isolation stops code leaking; the wire schema stops data leaking. Fetching a whole user record is no longer a vulnerability, because only declared fields are serialisable — which is a meaningfully stronger guarantee than "do not import the wrong file".

Two backstops, because inference can be wrong

  • Build-time scan. Every emitted client chunk is scanned for resolved secret values and for server-residency markers. A hit fails the build. This catches leaks through paths the graph did not model, including anything a plugin generated.
  • weft audit --bundle. Prints, per client chunk, every module in it and the import chain that put it there. Because residency is a graph property, "why is this in my bundle" is an answerable question — the same way weft why answers "why did this byte arrive when it did".

Enforcement

What happens when a budget is not met

The two halves of .budget({ js: '40kb', cpu: '80ms' }) are completely different mechanisms, and conflating them would be the easy mistake. One is known at build time and one is only knowable while a request is in flight.

The byte budget — build time, with the honest complications

js budget outcomes by context
ContextWhat happens
Local code, CIBuild fails, naming the slot, the measured size, and the diff against the previous build.
Local code, devWarning only. Blocking a local loop over 400 bytes is hostile, and a red CI is the actual gate.
Remote regionYou cannot fail your build on another team's regression. Checked at deploy by weft verify against what the remote actually serves, and again at runtime — an over-budget region is refused and its fallback() renders instead.

Two details that decide whether byte budgets are usable or merely satisfying:

  • Measure marginal cost, not gross. The number is the bytes this slot adds to the page given what the plan has already loaded. Gross measurement blames every region for the shared runtime, which makes budgets meaningless and gets them switched off.
  • Budget the growth, not just the ceiling. What teams actually want is budget({ js: '40kb', grow: '2kb' }) — a hard ceiling plus a cap on regression versus the base branch. A ceiling alone produces one painful renegotiation and then permanent silence at 39.8 KB.

The CPU budget — runtime, and only where preemption is possible

This one already has its mechanism: an executor boundary is a fault boundary, so onExceed is a policy applied when the executor is killed.

onExceed policies, in rough order of preference
PolicyBehaviour
'stale'Serve the last cached value even if expired. Stale-if-error semantics, and usually the best answer — the user sees real content.
'client'Abandon the server render and emit the island so the browser renders it. Degrades SSR to CSR for that one slot. Nothing else on the page notices.
'fallback'Render the declared fallback fragment.
'placeholder'Keep the skeleton. Honest, cheap, and visibly incomplete.
'fail'Propagate the error. Only defensible for a slot the page is meaningless without.
The wrinkle most designs would gloss over

A CPU budget is only enforceable on a preemptible executor. JavaScript is single-threaded: you cannot interrupt a synchronous render on the request thread. So on executor('inline') a CPU budget can only be checked cooperatively between awaits — it is advisory, and a tight synchronous loop will blow straight through it.

Declaring a CPU budget on an inline slot therefore produces a build warning: "cpu budgets are only enforceable on preemptible executors; this slot is inline — move it to pool:, isolate, binding:, or svc: for a hard limit." On those executors the budget is real: terminate the worker, abort the fetch, let the isolate die. This is a large part of why per-slot executors exist at all.

The envelope budget is a third thing again

Phase A's budget cannot be enforced by killing anything — aborting an auth check mid-flight is not a graceful degradation, it is a security decision. So it is measured and reported, the build warns when envelope work does I/O beyond its declared allowance, and at runtime a soft timeout drops optional envelope work while a required guard that times out fails the request properly. Delaying TTFB is the cost of correctness here, and the right response is to see it and restructure.

Graceful degradation hides problems — so make it loud

Every budget outcome is emitted through TelemetryPort as its own event class, the profile reports p95 against each budget, and weft why lists breaches. A slot silently degrading from SSR to CSR for 4% of requests is a real quality regression that looks like nothing at all in aggregate metrics.

This is the failure mode of graceful degradation generally, and it is worth designing against explicitly: the point of a budget is not only to contain damage, it is to tell you the damage happened.

Portability

Cloudflare Workers is the design target, not the deployment afterthought

Portability is not a checkbox you add with adapters at the end. It is a constraint on what the kernel is allowed to know. Design against the tightest runtime first and every other runtime is downhill.

The kernel speaks only standards

The rule is absolute: the kernel imports nothing but the WinterTC Minimum Common Web API — Request, Response, fetch, URL, Web Streams, TextEncoder, crypto.subtle, structuredClone. That surface was adopted as an Ecma standard in December 2025, which means it is now a real specification to conform to rather than a gentleman's agreement. Anything outside it — filesystem, sockets, process, Buffer, timers with Node semantics — reaches the kernel only through a port.

The payoff is that "runs on Workers" stops being a porting exercise. A Workers deployment is the kernel plus five small port implementations, and the same build output runs on Node, Bun, Deno, Fastly, Netlify, or a container with a different five.

Why this beats the incumbents on exactly this axis

Next.js use cache requires the Node runtime and the edge runtime rejects the directive outright — so the most sophisticated caching primitive in the most popular framework is unavailable on the runtime you want to deploy to. That is not an oversight, it is what happens when caching is a framework internal rather than a port.

Because a Weft cache key is derived from the effect signature and stored through StorePort, per-fragment caching works identically on a Worker isolate, a Node server, and a container. The mechanism does not know where it is.

Cache is a topology, not a boolean

Putting coherence in the interface matters more than it looks. An in-process cache you cannot invalidate remotely is not really a cache — it is a short buffer whose TTL you tune down until staleness stops hurting, which is how most teams end up with a two-second L1 and a poor hit rate. Naming the strategy forces the honest question, and the answers differ sharply by runtime: Redis 6+ can push per-key invalidations to clients that hold them via CLIENT TRACKING BCAST over RESP3, which is the most precise option available; a Worker isolate cannot be addressed at all, so it gets bounded TTL plus a generation counter and nothing more. Both are legitimate. Silently conflating them is not.

Three further properties fall out of putting lease and consistency in the interface rather than in framework internals. Stampede protection is universal instead of per-framework folklore. A misconfiguration — a strongly-consistent policy on an eventually-consistent store — is a build error. And set taking a ReadableStream means a fragment can be cached while it streams to the first user, rather than only after it completes.

Extension

Ports replace, plugins extend

Conflating these two is how plugin systems become unmaintainable. A port has exactly one active implementation and answers "who does this job". A plugin adds behavior at a defined point and answers "what else happens here". Both are first-class; neither substitutes for the other.

a plugin declares its surface up front
export default definePlugin({
  name: '@weft/i18n',
  // deterministic order without asking authors to count integers
  before: ['@weft/analytics'],
  after:  ['@weft/session'],

  // declared, enforced. reading anything unlisted throws in dev,
  // and silently taints nothing — the effect graph stays honest
  reads:   ['cookie:locale', 'header:accept-language'],
  provides: ['ctx.t', 'ctx.locale'],

  build: {
    transform(mod)      { /* extract message catalogs */ },
    planAxis()          { return { locale: ['en', 'ar', 'ku'] } }  // new cache dimension
  },

  runtime: {
    onRequest(ctx)      { /* resolve locale, taints the fragment */ },
    onPlanResolve(plan) { /* swap RTL stylesheet slot */ },
    onSlotOpen(slot)    { /* nothing */ },
    onFrame(frame)      { /* nothing */ },
    onFlush(chunk)      { /* nothing */ }
  }
})

The rules that keep it from rotting

  • Declared reads, enforced reads. A plugin that touches request state it did not declare throws in development. This is the single rule that protects the effect-tracking guarantee — without it, one careless plugin silently makes every fragment uncacheable, which is precisely how caching dies in real codebases today.
  • Plugins can add plan axes but never mutate keys. planAxis() lets a plugin introduce a new cache dimension — locale, tenant, currency, device class — and the kernel folds it into the derived key. A plugin can never write a key itself.
  • Relative ordering, not priority numbers. before and after form a DAG the kernel topologically sorts, and a cycle is a build error. Priority integers always end up as a war of magic numbers.
  • Scoped registration. A plugin registered on a route subtree or a single fragment affects only that scope and its descendants — Fastify's encapsulation model, which is the one plugin architecture in this ecosystem that demonstrably scales. Opting out to affect the parent is explicit and visible.
  • Build hooks and runtime hooks are separate objects. A plugin that only transforms modules ships zero runtime bytes, and the compiler can prove it. Today it is normal for a build-time-only integration to leak a runtime chunk.
  • Capability-gated, like everything else. A plugin that wants to register render intents or read identity declares it, and the app grants it. Third-party plugins get least privilege by default.

The dependency graph is inferred, so parallelism is free

Web frameworks universally model middleware as a sequential chain of responsibility, and it is a poor fit: in a typical eight-item chain, six items are independent lookups that pay sequential cost for no reason. Distributed systems solved this long ago by modelling read-write, write-read, and write-write relationships and executing the resulting DAG — where, as the literature puts it, parallelism is a consequence of the declared dependency structure and requires no concurrency code from developers.

We already have the declarations. reads and provides give the kernel everything it needs:

  • B reads what A provides → edge inferred. Nobody writes after: ['A'] for data flow; the graph derives it.
  • Disjoint reads and provides → concurrent. Locale resolution, tracing context, and flag hydration all run at once, in one wave.
  • Two plugins providing the same key → build error. Ambiguity is caught rather than resolved by load order.
  • before and after are only for ordering data flow cannot express — a CSP nonce must be injected before analytics adds a script tag, and no read/write relationship captures that. Hand-declared edges become rare rather than routine.

Filters short-circuit; enrichers do not

This split is the design move that makes the above safe, and it also dissolves the question of whether middleware is a separate concept. It is not — but there are two kinds of it, and they have different powers:

Plugins declare where they run, and what they may cost

residency, budget, and failure policy
definePlugin({
  name: '@acme/analytics',
  residency: 'both',          // 'server' | 'client' | 'both' | 'build'

  // a client plugin is budgeted exactly like an island.
  // this is how you stop four analytics plugins doubling the bundle.
  budget: { js: '3kb' },

  critical: false,             // failure is logged and skipped, not fatal
  timeout: '20ms',

  capabilities: ['network'],   // must be granted by the app. no identity, no storage.

  runtime: {
    onRequest(ctx) {},          // enricher — parallel
    onCommit(epoch) {}          // client hook — runs in the browser
  }
})

Residency is not a promise, it is checked: a server plugin's runtime code that ends up reachable from a client chunk is the same build error as any other residency conflict, with the same import trace. Client plugins get their own hooks — onFrame, onCommit, onNavigate, onIntent — and their own byte budget. Third-party plugins default to critical: false and receive no capabilities they have not been granted.

Concretely, this is the layer where things like auth, i18n, analytics, A/B assignment, CSP nonce injection, image optimization, and observability live — without any of them needing to be a framework feature, and without any of them being able to quietly break the guarantees that make the framework fast.

Protocol

Warp: one stream, five jobs

One logical channel per tab, with three transport bindings — see the Baseline audit that follows, because streamed request bodies are Chromium-only and cannot be the foundation. The initial document response is the first frames of that channel, emitted as ordinary HTML: out-of-order holes use declarative shadow DOM with slot assignment, filling with no JavaScript where incremental DSD parsing works and via a ~1 KB filler script where it does not. The channel then stays open and carries everything else in the same frame vocabulary.

The unification is available precisely because nobody wanted all five properties at once.

Deliberate consequence

Navigation becomes a frame, not a fetch waterfall. Mutations return single-flight responses on the connection that is already open. A post-load fragment refresh is the same three frames as the initial render. There is one thing to learn, one thing to debug, and one thing to optimize.

Correction one — "zero JavaScript out-of-order streaming" was too strong

Declarative Shadow DOM as a feature is Baseline. What is not uniformly verified is the incremental-parse semantics that make streaming work: attaching the shadow root on the opening tag so content inside can render as it arrives. Chromium tracks "streaming declarative shadow DOM" as its own feature entry, which is itself a signal that engine behaviour may differ.

That script has to exist and be tested regardless. The zero-JS row in the opt-out table should be read as "zero JS plus, at worst, 1 KB".

Correction two — Warp cannot use a streamed request body

I described Warp as a duplex channel. Streaming request bodies is Chromium-only, requires HTTP/2, requires duplex: 'half', and true full duplex does not exist in any browser. Building the uplink on it would make the framework Chromium-only at its core.

Warp is therefore a logical channel with three transport bindings. Default: streamed response downward — the initial document is the first frames — plus discrete POSTs upward. Alternative: WebSocket, the only Baseline true-duplex transport. Future: WebTransport, when Safari ships it. The frame vocabulary is identical across all three, which is the point of having a frame vocabulary.

One nuance worth knowing: reading a streamed response works everywhere via getReader(). It is the for await…of sugar over a stream that Safari lacks, and it has been proposed for Interop 2026. Use the reader.

  • requestIdleCallback is not Baseline. Safari ships it only behind a feature flag that real users will never enable, and scheduler.postTask is Chromium-only and still experimental. So when.idle compiles to a ladder — scheduler.postTask, then requestIdleCallback, then a setTimeout heuristic — and the plan must never assume idle callbacks fire.
  • HTTP/2 or /3 for Early Hints. Without it the 103 is simply not sent and phase A delays the first byte by its budget. Degrades to "slightly slower", never to "broken".

Why capability variance is not a special case here

The RESIDENT frame already carries client capabilities alongside RTT and CPU class, and form selection is already a per-request negotiation. So a browser lacking a capability is simply never offered the form that needs it — there is no feature-detection sprawl, no polyfill layer, and no separate code path to maintain.

This is the strongest practical argument for negotiation as an architecture rather than a feature: browser fragmentation is the same problem as network and cache variance, and it gets the same mechanism.

The central bet

Negotiated render form

This is the idea with the least prior art anywhere, and it is the one worth building the framework around. Every framework in existence freezes, at build time, the form in which a piece of UI travels. React ships HTML then chunks then a flight payload. Astro server islands always ship HTML over a fresh request. htmx and Datastar always ship HTML. Qwik always ships HTML plus lazy references. In each case the shape is a property of the framework, not a property of the request.

Make the wire form of a fragment a runtime negotiation over a set of encodings the compiler has proven equivalent — so the same UI can arrive as one inlined bundle, as code-split chunks, as a DOM patch, or as bare data projected through a template the client already holds.

Why only a compiler-first framework can offer this

The equivalence proof is the whole trick. Because templates compile to a wiring table plus pre-encoded byte segments, a fragment's output is a pure function of (template version, signal values). That makes html, patch, and data three encodings of one value, and the compiler can guarantee they produce byte-identical DOM. React cannot do this — component functions are opaque and re-render is not addressable. htmx cannot — there is no template on the client to project through. Qwik gets closest and never made the form negotiable. The capability is downstream of decisions this design is already making for other reasons, which is the sign of a good architecture rather than a bolted-on feature.

The client advertises what it already holds

Negotiation needs an input. Once per Warp connection the client sends a RESIDENT frame: a compact probabilistic set — a roaring bitmap or Bloom filter of a few hundred bytes — of the template hashes it has in cache, plus measured RTT, effective connection type, and CPU class. The server then answers in the cheapest sufficient form. A returning user refreshing a price list receives a DATA frame of a few dozen bytes where every other framework would re-send markup.

This rides on a real transport standard, not a hope

Compression Dictionary Transport — RFC 9842, shipped in Chrome and Edge 130+, Firefox in progress, and available at the Cloudflare edge in beta since April 2026 — lets a response be compressed against a previously fetched resource used as a dictionary. That is byte-level delta compression of exactly the redundancy this design creates deliberately.

The two layers compose rather than compete: the resident-set digest removes semantic redundancy by choosing a smaller form, and shared dictionaries remove byte redundancy from whatever form is chosen. Registering each template version as a dictionary is a natural fit, because template versions are already content-addressed.

Refreshing server data without re-rendering anything

"Refresh only part of the SSR data on the client" becomes a single frame. The client sends REFRESH s12; the server re-runs that one fragment — cheap, because its effect signature already gives it its own cache entry — and replies with the smallest sufficient form, usually DATA or a handful of SIGNAL frames. No markup travels, no component re-renders, and only the DOM positions bound to changed signals update.

The plan can declare it, so it is not something every app rebuilds:

declarative revalidation of a server-rendered region
slot('prices')
  .stream({ prio: 1 })
  .refresh(every('30s'), { when: when.visible.and(when.focused) })
  .form({ prefer: 'data', fallback: 'html' })

And because each slot carries a derived key and a version, invalidation can travel the other way: when a tag is invalidated, the store notifies open Warp connections holding affected keys and the server pushes STALE s12. The client decides whether to refresh now, on next focus, or never. That is push invalidation of server-rendered regions without turning the whole application into a realtime app — a middle ground nothing currently occupies.

Styles

CSS is a wire form too, and cascade layers are what make it streamable

CSS is uniquely hostile to streaming for three reasons: it blocks first paint, it is order-dependent because of the cascade, and it must arrive before the markup it styles or the user sees a flash. That third constraint is why flash-of-unstyled-content in streaming SSR is an open, documented problem across Qwik, Next with MUI, Nuxt 3, TanStack Start, and Quasar. The mechanism people report is always the same: style tags are emitted with components, then moved to the head, and the remove-render-reinsert sequence produces the flash.

The unlock: @layer makes arrival order irrelevant

Cascade layers are Baseline — Chrome and Edge 99, Firefox 97, Safari 15.4, above 96% globally — and their defining property is exactly the one needed here: layers are evaluated before specificity, a higher layer wins unconditionally, and the ordering holds regardless of how or when the files are loaded.

So assign every fragment's CSS to a layer structurally, from its role in the plan, and the cascade stops caring when bytes arrive:

emitted once, in the shell, before anything else
@layer reset, tokens, base, layout, component, island, utility, override;

This is the reason nobody streams CSS today and the reason we can. It is also why the ordering problem does not come back through the cache: a resident stylesheet restored from browser cache in a different order is still correctly ordered, because its layer is declared inside it.

CSS travels in the stream, ahead of its slot

A CSS frame precedes its slot's HTML frame on the same connection. The browser receives the rules before the nodes exist, so there is nothing to flash and nothing to move — we never emit a style tag inside the body and then relocate it, which is precisely the sequence that causes the documented bug. Deferred slots get their CSS at the moment their markup does, not upfront and not late.

Critical CSS is derived from the plan, not guessed from a viewport

The state of the art here is weaker than people assume. Critters is deprecated; Beasties is the maintained fork, and it is explicit about its limits — it uses no headless browser, so it is not aware of viewport size or which nodes are above the fold, and it inlines every rule the document uses rather than the above-fold subset. The workaround is a hand-placed data-beasties-container attribute.

We do not have to guess, because the plan already declares which slots are in the first flush. Critical CSS is therefore the exact union of styles reachable from those slots — computed per route, variant, and device class, and profile-selected like every other permutation. No headless browser, no marker attribute, no heuristic.

Elimination is exact, not text-scanned

Tailwind and its peers scan source text for class names, which is a heuristic that errs toward keeping too much. Our compiler emits the template's byte segments, so it knows every class that can actually appear in output — per fragment, per variant, per flag branch. A flag branch whose code is unreachable never ships its CSS either.

The honest gap in the layer story

Browsers without @layer ignore the declarations and fall back to specificity and source order. That is roughly 4% and shrinking, and it mostly does not matter because we control emission order — CSS frames are emitted in layer order, so source order is already correct for anything we send.

The residual risk is CSS we do not control the ordering of: a resident sheet restored from cache, or a deferred sheet arriving after a component sheet. Mitigation is boring and effective — the utility and override layers are always part of the inline critical block, never deferred, so nothing that needs to win can arrive late.

Render locus

Rendering does not belong on the thread that owns the stream

Everyone who runs SSR at scale already knows this. Yelp, Expedia, Tinkoff, and Wix have all published the same finding, and Wix reports cutting thousands of SSR pods by moving rendering off the main thread. Piscina exists because the pattern is universal. A Node worker thread is a full V8 isolate with roughly 10 MB of overhead and tens of milliseconds of startup, which is a cost worth paying because a synchronous render of 10–100 ms otherwise blocks every other request on that process.

And yet no framework exposes it. It is operational folklore, rebuilt per company, sitting outside the framework that caused the problem. Make it a declaration:

where a render executes is a per-slot property
slot('report')                      // heavy, CPU-bound, must not block the stream
  .executor('pool:heavy')
  .budget({ cpu: '120ms', onExceed: 'placeholder' })

slot('header').executor('inline')  // trivial, stays on the request path
slot('reviews').executor('svc:reviews') // another team's deployment

ExecutorPort has one method — take a fragment and its params, return a stream of Warp frames — and that single signature collapses six things that are normally six unrelated mechanisms:

  • inline — same thread. The default, and the fastest for cheap fragments.
  • pool — a worker-thread pool. Node worker_threads, Bun or Deno Worker.
  • isolate — a separate V8 isolate with its own heap and its own crash domain.
  • binding — a Cloudflare service binding. Notably, service bindings add zero network latency by default because both Workers run on the same thread of the same server, which is what makes fine-grained splitting viable there at all.
  • svc — an HTTP call to another pod or Lambda that speaks Warp.
  • client — do not render on the server at all; emit the island and let the browser do it. Optionally in a browser Worker, since patches are data and can be produced off the main thread too.

Two consequences beyond throughput. First, the executor boundary is a natural fault and budget boundary, so a fragment that blows its CPU budget is killed and its slot degrades to a placeholder or a client render — per-slot fault isolation, which matters enormously on a platform with a hard per-request CPU limit. Second, a local heavy fragment and a third-party micro-frontend become the same abstraction differing only in binding target. The micro-frontend story stops being a separate subsystem.

Currency

Fresh data without a changed view

Everywhere in the current ecosystem, fetching implies committing. A background revalidation repaints. A prefetch that warms a shared cache can disturb the view you are looking at. TanStack Query's staleTime refetch re-renders; React's Transitions defer the render but give you no addressable handle on a fresh, uncommitted dataset. Separating data currency from view currency is the missing primitive.

Epochs

The signal graph carries generations. live is what is painted; any number of staged epochs may exist alongside it, fully resolved and completely invisible. Frames name their target — DATA s12 epoch=e7 lands in staging and paints nothing. COMMIT e7 flips every slot staged in that epoch, atomically, optionally wrapped in a view transition.

Four things become straightforward that are currently awkward or impossible:

  • Prefetch can never disturb the present. Speculative data lands in a staged epoch, so the classic bug where prefetching a route flickers the current one is structurally impossible rather than carefully avoided.
  • Revalidate while the user works. Fresh data can sit staged through a scroll, a text selection, or a half-typed form, and commit at the next safe moment — on blur, on idle, on navigation, or never.
  • Atomic multi-slot commit. Stage five slots, commit once. The page never shows a half-updated state. This is a transaction boundary for UI data, and nothing currently offers one — every framework updates slot-by-slot as responses land.
  • Optimistic updates that can be dropped cleanly. An optimistic mutation is a staged epoch committed immediately; rollback is discarding an epoch rather than reconstructing prior state.
the three readiness layers of a predicted navigation, declared once
predict(when.hover('a[href^="/checkout"]'), { delay: 80 })
  .speculate('prerender')        // browser: Speculation Rules, document level
  .discover()                    // warp:    PLAN extend — routes, chunks, css
  .warm({ epoch: 'next' })       // warp:    slot data, staged, unpainted

Route-level data prefetch on intent is well-covered ground — TanStack Router has preload-on-hover with a 50 ms default delay, preload-on-viewport via IntersectionObserver, and a 30-second GC of unused preloads. Three things there are still open, and all three matter: prefetch happens at route granularity rather than per slot with its own cache key; there is one wire form rather than a negotiated one, so a client already holding the template still receives markup; and the preload lands in the same cache the live view reads, which is what makes prefetch risky today. Epochs plus slot-granular keys plus form negotiation fix all three, and coordinating with the browser's own prerender is free once prediction is a declared signal rather than scattered link props.

A neat fit with the platform

Chrome 144 added a prerender mode that fetches HTML and begins rendering and subresource loading but pauses JavaScript at the first blocking script — no analytics fires, no side effects, but CSS, images, and fonts all load.

For a design whose first flush needs no JavaScript to be meaningful — out-of-order holes filled by declarative shadow DOM — that mode delivers a nearly complete page. Most frameworks get much less from it because their shell does nothing until scripts run. It is Chromium-only, so treat it as upside rather than strategy.

The hardest part

Surgical updates without a stateful server

This is where the honest answer is that someone got there first, and got there properly. Phoenix LiveView is the strongest prior art in this entire survey, and understanding exactly what it does — and the one thing it structurally cannot do — is what defines the opportunity.

What LiveView already solved

LiveView's template engine splits a template into static and dynamic parts. The first render sends both. Every subsequent render sends only the dynamic parts, and only those whose backing assigns actually changed, tracked through a changed-map. The wire format is binary and compact. As the documentation puts it, one mechanism solves two problems at once: not executing the dynamic parts that did not change, and not sending them either. Server-side minimal recompute and client-side minimal patch, from a single design. Blazor Server reaches a similar destination more expensively — it re-executes the render tree, diffs against the previous tree, and batches the resulting DOM operations over SignalR.

The one thing it cannot do

Both require a stateful process per connected user, holding the previous render in memory. That single requirement rules out serverless and edge runtimes, forces sticky sessions, makes memory scale with concurrent users, and — most consequentially — means a diff is computed per connection and can never be shared. If ten thousand users are looking at the same price list and it changes, LiveView computes ten thousand identical diffs in ten thousand processes.

Keep the render state on the client, not the server. The client names the base render it holds; the server recovers that base from the cache, recomputes the affected subgraph, and emits the delta. Any stateless isolate anywhere can serve it — and because keys are content-addressed, the delta itself is cacheable.

The mechanism

a stateless surgical refresh, end to end
client →  HELD    s12=a91f-abc123        // template a91f, data version abc123
          REFRESH s12 form=auto

server:  1. recover base abc123 inputs via StorePort  (L1 → L2)
          2. re-execute only the subgraph whose inputs changed
          3. diff dynamics → {2:"12,400", 5:"in stock"}
          4. memoize delta under key  abc123→def456

server →  DELTA   s12 base=abc123 next=def456 {2:"12,400",5:"in stock"}

client:  wiring table says binding 2 → text node, binding 5 → text node.
          two writes. no diffing, no template execution, no vdom.

Every step degrades safely, which is what makes it deployable rather than clever. Base not in cache → send data. Template not resident → send html. No Warp connection at all → a plain request returns a full response. The fast path is an optimisation over a correct slow path, never a replacement for it.

Why the shared delta matters more than it sounds

Ten thousand clients holding prices@abc123, transitioning to def456, need one delta computed once and served ten thousand times from L2 or the CDN. The delta is a pure function of two content-addressed states, so it is cacheable by exactly the same machinery as everything else — no new subsystem. This is the single largest efficiency argument for content-addressing the whole design, and it is unavailable to any framework that holds render state server-side per connection.

Incremental recompute on the server

"Little overhead on the server" means not re-running work whose inputs did not change. The theory here is mature: self-adjusting computation builds a dynamic dependence graph recording control and data dependencies, then recomputes a minimal subset when inputs change. Adapton made it composable and demand-driven; Salsa is the production Rust implementation that makes rust-analyzer feasible. None of it has been applied to server-side HTML rendering as a general framework primitive — LiveView's static/dynamic template split is the closest practical instance, and it is per-template rather than a general memoized graph.

Three memoisation levels, each keyed by content hash:

  • Fragment — keyed by the effect signature. Already in the design; this is the coarse win.
  • Derived value — every computation node inside a fragment keyed by the hash of its inputs, so a changed price does not re-run an untouched permission check.
  • Template segment — pre-encoded bytes, reused verbatim whenever the values feeding them are unchanged.
The known weakness, stated rather than glossed

The incremental-computation literature is explicit that changes to the structure of the computation graph are the hard case — and HTML rendering changes structure constantly, through conditionals, list reordering, and mounting or unmounting subtrees.

So this is opt-in per slot via .incremental(), not a global mode. Memoisation costs input hashing and node storage, and it only pays where the graph is structurally stable and the recompute is expensive — a pricing table, a permissions matrix, a rendered document. For a slot that is cheap to render outright, it is pure overhead, and the tooling should say so rather than letting people discover it.

Evaluation order

Render is a DAG, not a tree walk

Every server renderer in production today walks depth-first from root to leaf on one thread. Streaming lets async boundaries yield, but the walk itself is still sequential — so a page with forty independent sections evaluates them one after another, and a three-level nesting where each level fetches for 30 ms costs 90 ms instead of 30.

Remix and React Router solved this at the route level by running all loaders in parallel before rendering, which is the right instinct. Nobody has generalised it to arbitrary page structure, because in most frameworks it would not be safe.

Existence dependency is not data dependency

The conflation at the heart of the problem: a child cannot start today because the parent decides whether it exists — not because the child needs the parent's data. Separate those two and most of a page becomes parallelisable.

  • Statically-known subtrees — a fragment composed unconditionally — have their existence known at build time. They can be dispatched immediately at request time, without waiting for the walk to reach them.
  • Data-dependent fragments — where a child's props genuinely derive from a parent's result — must wait, and the compiler knows which those are because props flow is visible in the graph.
  • Conditional subtrees are the interesting middle: speculate, or wait. That becomes a declared choice — .speculate(true | false | 'profile') — with the profile deciding when a branch is taken often enough to be worth the wasted work.

Note what most props actually look like. <CartLines currency={currency} /> takes a value that came from a cookie read, not from a sibling's output. The child depends on its parent's decision, which is static, not its parent's data, which is not. That pattern dominates real pages, which is why the available parallelism is large.

Independent fragments dispatched into different pool workers or service bindings give genuine CPU parallelism rather than merely overlapping I/O — which is the point of having per-slot executors in the first place. And because slots already stream out of order, completion order does not need to match document order.

This is safe here and unsafe in React for one specific reason: render is provably read-only. Envelope writes are confined to phase A, mutations are confined to intents, and effects are tracked — so two fragments evaluated concurrently cannot observe each other's side effects, because they cannot have any.

In a framework where a component may write to a store, dispatch an action, or set a cookie mid-render, parallel evaluation makes ordering observable and the result nondeterministic. The constraint that made the envelope design necessary turns out to be the constraint that makes concurrent evaluation possible. That is worth noticing: it is the same invariant paying twice.

The hazards, which are real

  • Connection-pool exhaustion. Forty concurrent queries from one page request will melt a database. Concurrency is capped per request and per executor, declared in config, and the build warns when a route's wave width exceeds it.
  • Memory in flight. N fragments resolving simultaneously each hold results. Inside a 128 MB Workers isolate that is a hard ceiling, so wave width is bounded and fragments stream rather than buffer.
  • Wasted speculation. A speculated branch that is not taken is thrown away. Only worth it for cheap fragments or high-probability branches, which is a profile question, not a taste question.
  • Debuggability. Concurrent evaluation makes stack traces less linear. The DAG view above is the mitigation, and it has to exist before the feature does.

Variants

Multi-tenant and multi-brand, replaceable piece by piece

Two established patterns solve parts of this. Nuxt Layers let a tenant layer extend a base app and override only what differs — a branded header, a different layout, tenant config — with the consuming project always winning. React Native resolves .ios.tsx and .android.tsx by platform, and Android's resource qualifiers generalise that to many dimensions with a documented precedence table. Both patterns work. Neither is typed, neither is multi-dimensional and typed, and neither knows anything about caching.

A variant is a typed tuple of dimensions

app/variants.ts — declared order is precedence order
export const brand = dimension('brand', ['sindibad', 'acme'], {
  resolve: 'build'            // separate artifacts. other brands' code cannot leak.
})

export const device = dimension('device', ['mobile', 'desktop'], {
  resolve: 'request'          // one artifact, resolved per request, enters the key
})

export const tenant = dimension('tenant', dynamic(), {
  resolve: 'request',
  from: ctx => ctx.header('x-tenant')   // unbounded cardinality
})

The resolve choice is the important fork, and both halves have to work from the same source — which is exactly what neither existing pattern manages. Nuxt Layers are build-time only; multi-tenant SaaS is invariably runtime-only.

  • resolve: 'build' — the dimension becomes a build matrix. N artifacts, zero runtime cost, and cross-brand leakage is physically impossible because the other brand's code is not in the bundle. Right for a handful of white-label brands on separate deploys.
  • resolve: 'request' — the dimension becomes a plan axis and a cache-key component, resolved at the gateway. One deploy, many tenants.
  • dynamic() — unbounded, so it cannot be a build matrix. The profile picks the hot tenants to prebuild; the tail renders on demand. This is where profile-guided delivery stops being a nicety.

Two override syntaxes, one mechanism

qualified files for surgery, layer directories for divergence
// (a) qualified filenames — most specific match wins

Where Android's precedence rules are famously subtle, ours are boring on purpose: the declaration order in variants.ts is the precedence order, and any genuine ambiguity is a build error rather than something resolved by a rule people have to memorise.

An override must satisfy the base's contract

This is the failure mode of every theme-inheritance system: the base changes, the override silently drifts, and nobody finds out until a customer does. So overriding is type-checked against the base — same props, same wire schema or a subset of it, same intents. Add a prop to the base and every override fails to compile, naming each one.

// variants/acme/routes/cart/cart-lines.tsx

  // only the template differs.

    return <AcmeList items={base.lines} theme="acme" />
  }

plans are overridable too — "extending the app to the view part"

Because reading the tenant taints the fragment, every cache key includes the resolved variant automatically. Cross-tenant cache leakage — one of the most persistent and damaging bugs in real multi-tenant systems — becomes structurally impossible rather than a thing you remember to test.

What falls out for free

  • Sharing is the economics, and it is measurable. A fragment nobody overrode is one cache entry serving every tenant. An overridden one is not. So the interesting number is the share of fragments that are common — weft variants reports exactly that, alongside bundle size per variant and the cache-sharing ratio.
  • Variant residency reuses the isolation machinery. A shared fragment importing a tenant-specific module is the same build error as any other residency conflict, with the same import trace. Tenant A's client cannot receive tenant B's templates.
  • Fog of war becomes a tenancy boundary. A client only ever learns about the routes and templates it has actually visited, so one tenant's client never discovers that another's surface exists.
  • Variants are just another plan axis, so they compose with flags, device class, and locale without new machinery — and the combinatorial explosion is already handled by prebuilding to a profile-driven coverage target rather than exhaustively.

Orchestration

The app shell is a plan that composes other plans

Micro-frontend orchestration is currently a separate product category with its own runtime, its own registry, and its own failure modes. It should not be. A shell is a fragment tree whose leaves are regions, and a region is a fragment that happens to live somewhere else.

Honest credit first

single-spa established the model: a root config with no business logic that registers applications by name with an activeWhen predicate, and drives bootstrap, mount, and unmount lifecycles across framework boundaries. It is widely deployed and the shape is right. Its documented hazard is instructive — incorrect lifecycle handling produces memory leaks, UI conflicts, and unexpected behaviour, because lifecycle correctness is the application author's responsibility.

Module Federation solved the dependency half. singleton: true with strictVersion: true throws when several versions of a shared package appear at runtime; requiredVersion defines semver scopes. Type safety across remotes exists via a TypeScript plugin that generates declaration files from remote modules, and the recommended discipline is contract tests in CI against the remote's published types — with the blunt observation that teams who skip it learn about version skew from their users.

So typed cross-boundary contracts are not novel, and I should not pretend otherwise. What is missing is narrower and more specific: those contracts are verified in CI against published types rather than against what production is actually serving at the moment of deploy, and the runtime failure mode is either an exception or silently loading a duplicate copy — never a declared, degraded fallback.

The design

shell.plan.ts · a shell is a plan, so it inherits everything
export default shell(({ region, contract }) => {

  region('chrome').local('./chrome').critical()   // ours, first flush

  region('search')
    .remote('svc:search', contract.search)          // generated type, checked
    .budget({ js: '40kb', cpu: '80ms' })
    .fallback('static:search-placeholder')          // declared degradation
    .csp({ 'connect-src': ["'self'", 'https://search.internal'] })

  region('recs')
    .remote('svc:recs')
    .optional()                                    // failure is invisible
    .executor('client')                            // CSR, below the fold

  // typed, explicit, and the only channel between regions
  expose({ locale: signals.locale, cartCount: signals.cartCount })
})

Five things follow from the shell being a plan rather than a separate runtime:

  • It inherits the whole design. Derived cache keys for the composite, negotiated wire form per region, executors per region — inline, worker pool, service binding, remote pod — epochs, profile-guided ordering, streaming holes. None of it is re-implemented for micro-frontends because none of it knows the difference.
  • It composes server-side and client-side over one protocol. Existing orchestrators are either client-side runtimes that mount applications into a shell, or server-side gateways that stitch HTML. This one does the first flush server-side and subsequent region swaps client-side using the same Warp frames, so there is no seam between "how the page arrives" and "how it changes".
  • Contracts are verified against production, not against a registry. weft verify --against production queries what each remote actually serves and refuses a deploy whose expectations do not match. CI contract tests against published types remain useful; this closes the window between publishing a type and serving a version.
  • Failure is declared, not discovered. optional() means a dead region renders nothing and nobody is paged. fallback() means it renders something known-good. Budgets kill runaways. This falls out of executors already being fault boundaries — the orchestrator gets per-region isolation for free rather than needing lifecycle discipline from every team.
  • Shells nest. A shell is a fragment, so a product shell can be a region of an organisation shell without a second mechanism. Registry, budgets, contracts, and CSP compose down the tree.

The registry is a port, which is what makes it portable

RegistryPort resolves a region name to a deployment. Back it with a checked-in file, a KV namespace, Consul, a control plane, or your own service discovery. Rolling a region to a new version becomes a registry write rather than a shell redeploy — and because the orchestrator holds no render state, it scales horizontally with connections like any other gateway. Region fan-out is declared in the plan, so worst-case hop and subrequest counts are computable at build time rather than discovered under load.

Topology

Scale the parts, not the process

Because every capability is already a port and every executor already returns Warp frames, the framework itself decomposes. A tier boundary is just a port whose implementation is remote — there is no translation layer to write, because the internal protocol and the wire protocol are the same protocol.

  • gateway tierTerminates Warp connections, resolves flags, serves L0/L1 shell buffers, frames and flushes. Tiny and stateless. Scales with concurrent connections. Never makes a hop for the first flush — that is the whole point of putting pre-encoded shells here.
  • render tierExecutes fragments. CPU-bound, poolable, autoscaled on render load, placeable near data. Holds warm template caches.
  • store tierCache, tag index, stampede leases. Scales with read volume and invalidation fan-out.
  • flag tierFlag resolution and payload assembly. Read-heavy, highly cacheable, often just KV.
  • authority tierValidates render intents, checks capabilities, verifies signatures. Small, security-sensitive, deliberately separable so it can be audited and rate-limited on its own.

Named topologies, one codebase

same build output, four deployment shapes
'monolith'       // everything in one process. THE DEFAULT. zero infra, laptop-friendly.
'split-render'   // gateway + render pool. the Wix/Yelp shape, as config.
'edge-regional'  // edge gateway worldwide + regional render tier near the database.
'mesh'           // every tier independent; render fans out to per-team fragment services.

On Cloudflare the whole tiered shape exists natively with no orchestration at all: a gateway Worker, render Workers reached by service bindings, a Durable Object holding stampede leases, and KV or R2 as the store. On Kubernetes it is four deployments. On a laptop it is one process. The build output does not change.

Honest cost, stated up front

Service bindings make splitting cheap but not free — each call adds latency even when sub-millisecond, and each tier adds deployment, versioning, and cognitive overhead. Decomposition must therefore be opt-in per slot, never a global mode, and the collapsed single-process topology has to remain the default and the best-tested path.

The plan makes the cost visible instead of theoretical: because per-slot executors and fan-out are declared, the build can report a route's worst-case hop count and subrequest count, and warn before it approaches the platform ceiling.

Tiering buys graceful degradation, which is most of the point

Splitting for scale is the obvious motive. The better one is that a tier boundary is a failure boundary, so a partial outage becomes a degraded page rather than an error page:

The one genuinely stateful component

Every tier above is stateless and replicates freely, which is what makes the client-carried-render-state decision pay off. Push invalidation is the exception: sending STALE to the right clients needs an index from cache tag to live connection, and live connections are state that must live somewhere.

On Workers a connection is held by a Durable Object and a second DO class shards the tag index by tag hash. On Kubernetes connections live in gateway memory with a local tag map, and invalidation fans out over pub/sub to every gateway — no sharding required, because each gateway indexes only its own connections. And the whole tier is optional: switch it off and clients revalidate on focus or on their declared interval instead. Saying that plainly is more useful than implying it is free.

What platform-agnostic actually has to mean

Three commitments, all falsifiable:

  • No proprietary primitive above a port. The kernel is WinterTC Minimum Common API only. Durable Objects, KV, waitUntil, worker_threads, Redis, and S3 all appear exclusively as port implementations. If a feature cannot be expressed against the standard surface, it does not go in the kernel.
  • Every tier boundary is a standard stream boundary. Warp over HTTP with a Web Streams body. That works over a service binding, an in-process function call, a pod-to-pod request, or a Lambda invoke, without a per-platform protocol.
  • Zero-infrastructure default. Infra-agnostic includes no infra. weft dev and weft start must run the full framework — caching, tiering semantics, streaming, refresh, negotiation — in one process with no external dependency. A framework that needs a cloud account to demonstrate its own caching has already failed this test.

Client

Resumption without closure serialization

Qwik was right about the goal and wrong about the mechanism. It serializes closures because its component model is React-shaped, and closure serialization is what produced both the payload cost and the $ sigils that made it feel alien. With a compiler and a fine-grained signal graph, resumption collapses into something much smaller:

  • No hydration pass at all. The server emits, alongside the HTML, a compiled wiring table: signal ID → DOM position (node, attribute, or text offset), and DOM event → intent ID.
  • Only values are serialized. Signal values, not closures. The wiring table is content-addressed and cacheable across users, because it depends on the template, not the request.
  • No sigils. Nothing in authored code marks a lazy boundary. The compiler derives island boundaries from reactive reachability — extending what Marko already proves is possible — so what ships is exactly what can change.
  • Forward-compatible reactivity. Build the graph on the TC39 Signals shape so the runtime can be shed later when it standardizes. Target 4–6 KB for the client core.

Stated plainly, as the technical claim to defend: resumability does not require serializing closures; it requires a compiler and a lookup table.

Authoring

New syntax, but only where it earns its keep

Components stay TSX-shaped. This is a deliberate concession to tooling: a new component dialect means new editor support, new linters, new formatters, new codemods, new type-checking, and a workforce that has to learn it — an enormous cost for very little gain, since a compiler over TSX already reaches the right performance tier. Remix 3 reduced its own domain-specific language for a closely related reason, and the reasoning holds.

The delivery plan is where a new declarative surface genuinely pays, because there is nothing to be compatible with and everything to gain from being checkable:

Ahead of time

The plan should be compiled against a profile, not written by hand

This is the idea that retroactively justifies the whole thesis. If delivery decisions are scattered across link props, dynamic imports, and framework internals, there is nothing to optimise. If they are one declarative artifact, that artifact can be generated from production data — which is exactly what native toolchains have done for twenty years and the web has never done.

What a profile actually decides

TelemetryPort already emits the plan's named milestones as RUM marks, so the feedback loop closes without new instrumentation. weft profile consumes the resulting field data and emits a profile artifact the build reads:

  • Prebuild set. The observed distribution over flag-set × locale × device class, cut at a coverage target — "prebuild until 95% of traffic is served from a buffer". This is the answer to the precompute explosion: Vercel's pattern builds every permutation because it has no idea which ones matter.
  • Flush order. Measured per-slot p50 and p95 resolve latency becomes the scheduler's static priority hint, so the usual case is fastest-first without runtime guessing.
  • Chunk packing. Observed co-request sequences merge chunks that always travel together and split ones that do not. Straight BOLT-style layout, applied to JavaScript.
  • Default wire form per slot. Measured resident-set hit rate: if 90% of arrivals at /cart already hold the cart template, default that slot to data and treat html as the exception.
  • Island load conditions. Observed interaction rates convert when.idle into when.interaction for the island only 3% of users ever touch — and the reverse for the one everybody uses.
  • Speculation eagerness. Measured hover-to-navigate conversion per link class decides where a full browser prerender is worth its cost. Prerendering is expensive; today the eagerness setting is a guess.
  • Compile hints and budgets. Chunks always executed on load get the eager-compile marker. Routes with poor field LCP get enforced byte budgets. Both from data rather than intuition.

Ahead-of-time rendering, in three senses

  • Static fragments. Anything whose effect signature is empty is resolved at build and written as a file. Derived, not annotated — which is the difference from partial prerendering, where a human draws the boundary.
  • Hot permutations. The profile-selected cross-product of low-cardinality inputs, pre-encoded as complete shell buffers. The tail renders on demand and nobody notices.
  • Hot deltas. Common state transitions — logged-out to logged-in, currency switch, flag rollout boundary — have their deltas precomputed at deploy time. Because a delta is a pure function of two content-addressed states, this is just cache warming, not a new mechanism.
The honest prior art

Guess.js did attempt this on the web, in 2018: it pulled a Google Analytics report at build time, trained a Markov-chain or neural model of navigation, and prefetched the bundles for the top-N predicted next pages, reporting around 20% better perceived load. It was narrow — prefetching only — and it is dormant.

Everything else points the other way. The 2026 RUM tooling landscape has build plugins that push artifacts to the monitoring service — source maps, deobfuscation data. Nothing feeds production profiles back into delivery decisions. The loop exists in native toolchains as AutoFDO and does not exist on the web.

Why this is also the best answer to the DX objection

The obvious complaint about this whole design is that per-slot priorities, forms, executors, and load conditions are a lot to hand-tune. They are — which is why you should not hand-tune them. You write nothing, the profile generates the plan, and you hand-write only deliberate overrides.

And because the generated plan is a checked-in file, a delivery regression shows up as a plan diff in code review. Someone adds a cookie read and the reviewer sees a slot move from shared to private. Someone adds a dependency and the reviewer sees two chunks merge and a budget breach. No framework can currently surface a performance change as a reviewable text diff, because no framework has an artifact to diff.

Two consequences worth naming

Fog of war, generalized — and render authority, inverted

The plan is the manifest

React Router's Fog of War applies lazy discovery to routes and stops there. Here the plan is already the unit of knowledge, so extending it lazily generalizes for free — routes, island chunks, CSS, flag payloads, and data schemas all arrive on a PLAN extend frame, triggered by link hover, viewport proximity, or an explicit router.discover('/checkout/*').

This is also a security property, not only a performance one. Unvisited surface area is genuinely absent from the client, and flag names are hashed by default — which the production teardown cited earlier shows being done by hand, specifically to keep an unreleased roadmap out of the browser.

The client can never name a component

The build emits a catalog of render intents: intentId → (fragment, param schema, required capabilities). The client sends INTENT 7f3 {id: 42} — an opaque ID and typed params, never a code reference. The kernel validates params against the generated schema, checks capabilities against the session, and only then renders. High-value flows can additionally require signed, expiring intent tokens, which is exactly the Ed25519-signed-layout discipline mobile SDUI has used for years.

Paired with per-slot renderOn: 'server' | 'client' | 'either' that the compiler enforces by refusing to emit client code for server-only slots, this is your security hinting requirement turned into a build failure rather than a code review.

Micro-frontends fall out for free

A fragment is already addressable, independently streamable, and owns its own plan, cache key, and island set. A remote fragment is therefore just a fragment whose RenderPort makes an HTTP call to another deployment that speaks Warp. No iframes, no module federation runtime. Style isolation is opt-in shadow DOM, script isolation is per-fragment CSP, and cross-fragment state is explicit: typed expose / consume signal contracts, so coupling is visible in types instead of accidental.

Reactivity stance

No virtual DOM, and no component re-render either

The virtual DOM question is settled. Vue 3.6 reached release candidate in July 2026 with Vapor Mode feature-complete, compiling templates straight to imperative DOM operations; Solid never had a VDOM; Svelte 5 rebuilt reactivity around runes and compile-time tracking. What matters now is being precise about what else goes with it.

What is deliberately absent

  • No virtual DOM, no reconciliation, no tree diffing. Updates are signal writes into positions a table already knows.
  • No component re-render. A fragment's body runs once. There is no second invocation to reason about, so no memo, no useMemo, no useCallback — memoisation is structural rather than a thing you sprinkle.
  • No hooks and no rules of hooks. Signals are values, so they can be created conditionally, in loops, or in helpers.
  • No dependency arrays. Effects track what they read.
  • No key-based list reconciliation. Keyed lists compile to explicit move, insert, and remove operations rather than a heuristic diff.
  • No synthetic event system. Native delegation at the root, dispatched through the wiring table.
  • No 'use client', no 'use server', no RSC payload. Residency is inferred; the client never names server code.
  • No hydration mismatch, as a bug category. The client never re-renders in order to compare, so there is nothing to mismatch — it adopts nodes by position from a table the server generated.

The double-data problem, solved by construction

Server-rendered frameworks send most data twice: once as rendered markup, and again as a JSON blob so the client can hydrate. Partial-hydration frameworks reduce it by serialising only what top-level client components need, which helps and does not fix it.

The wiring table makes the fix structural. It already maps every signal to an exact DOM position — so the client reads the initial value out of the DOM rather than receiving it again. A text binding's initial value is the text node's content. A disabled state is the attribute. The only values that must be serialised are the ones not recoverable from the markup: a record id, a cursor, a field that is held but not displayed.

The initial state payload is therefore a compiler-provable minimum — precisely the complement of what the markup already shows. Not a smaller blob: the smallest possible blob, computed as wire schema − recoverable-from-DOM.

The second kind of double fetch disappears too. There is no fetch-on-mount because there is no mount, and no query cache to rehydrate because the server never hands the client one — it hands it signals already wired to the DOM. A refresh is an explicit REFRESH frame, not a lifecycle side effect that fires because a component happened to render.

The granularity axis nobody has pushed on

Signals made the update path fine-grained everywhere. The loading path is still coarse in every framework, because an island is simultaneously the unit of reactive scope and the unit of code delivery. One interactive button drags its whole module along.

A wiring table decouples those, because it is data rather than code:

  • The unit of interactivity is a binding, not a component. A page can hold two hundred reactive bindings while having fetched code for none of them.
  • Handler code loads per handler. A table entry points at a chunk. Qwik proved this works with QRLs and paid for it in closure serialisation; a table needs none.
  • Bindings have readiness tiers. Cold — wired, handler not fetched. Armed — handler prefetched, not executed. Live — running. The plan and the profile choose per binding. Per-binding readiness has no precedent I can find.
  • Most handlers need no client code at all. A table entry saying click → intent 7f3 is dispatched by a shared runtime of a few hundred bytes.
Why that last point matters more than it sounds

Take an ordinary commerce page: add to cart, quantity, wishlist toggle, filter, sort, paginate. Every one of those is server-authoritative — the client's job is to tell the server something and update part of the page. An island model ships a component for each. Here each is one wiring-table entry plus an intent id, handled by the same shared dispatcher.

So the page's client JavaScript is the runtime plus whatever is genuinely client-only — a date picker, a canvas chart, a drag interaction. Islands ship components to do what a table entry can do, and that is the specific inefficiency to attack.

Performance

How you would actually beat everyone

"Faster than any framework" is only defensible against a benchmark you publish and others can run — and it should be stated per axis, because on one of the obvious axes the honest answer is that we will tie.

Where there is no headroom left

Isolated DOM update cost is at the floor. Solid, Svelte 5 runes, and Vue Vapor all compile to direct imperative DOM operations driven by fine-grained signals, and Vue's own Vapor results are reported as landing in the same range as Solid and Svelte. A signal write followed by one targeted DOM mutation is close to the minimum a JavaScript engine can do. Claiming to beat them on js-framework-benchmark-style update rows would not be credible. We should publish those numbers anyway — to demonstrate we are at the floor rather than below it — but they are not the differentiator, and a design that markets itself on them is marketing a tie.

Every client-side-rendering benchmark measures the JS path and therefore measures the thing we deliberately avoid. That is a reason to build our own harness, not a reason to distrust theirs.

The levers

  • Templates compile to pre-encoded bytes. Arrays of constant Uint8Array segments with interpolation points, so SSR is memcpy plus escaping rather than string concatenation. This is where Marko and Solid already win; caching the encoded bytes pushes it further.
  • Zero-copy first flush. The static head and shell are precomputed per reachable (route × flag-set × device-class) at build time and served as a single pre-encoded buffer. TTFB becomes a lookup, which is how you get under the 50–65 ms that a well-tuned real SSR app achieves today.
  • No async on the critical path, by construction. The kernel requires the shell fragment's reads to resolve synchronously — flags inlined at the edge, cookies parsed lazily. Anything asynchronous is necessarily a hole, so a slow query cannot delay first paint.
  • Escape elision. The compiler proves which interpolations are already safe — numbers, enums, values from sanitizing sources — and skips escaping them entirely.
  • Headers and preloads before data. Always flushed first, never opt-in.
  • Fastest-first scheduling. Because slot order is data rather than control flow, the scheduler fills the pipe with whatever is ready instead of blocking on document order.
  • CSS per route and per island, emitted in the flush that needs it, with blocking=render reserved for above-the-fold only.
  • Native core later, not first. A Rust or Zig template renderer and frame codec is a plausible phase-five optimization. Starting there would kill the project.

Future-proofing

Changing the syntax later, and supporting other frameworks

This is answerable precisely rather than hopefully, because the component layer has a definite job. Whatever sits there must produce four things: pre-encoded byte segments with interpolation points, a wiring table mapping bindings to DOM positions, an effect signature, and derived island boundaries. Anything that can produce those gets everything. Anything that cannot is limited in a specific, predictable way.

The decision that has to be made now, while there is only one dialect: define the compiler's intermediate representation as a first-class, versioned, documented artifact. If the runtime consumes only the IR, a second dialect is a new front-end for the same back-end. If compiler and runtime are entangled, adding a dialect means rewriting both.

That is the standard compiler answer and it is cheap today and brutally expensive to retrofit. The IR carries the template segments, the wiring entries, the effect signature, island boundaries, intent references, and the wire schema. It is serialisable, inspectable, and independently testable — so a third-party dialect is validated by one question: does it emit conforming IR?

Honest counterpoints

What would kill this

Architecture does not win adoption.Qwik is the proof. It was technically ahead and lost anyway. A new protocol plus a new plan DSL is a real ecosystem tax, and the only defense is that the component layer stays boringly familiar.
Effect tracking leaks through any escape hatch.One direct req.headers or process.env read punches a hole in the entire cacheability guarantee. This needs a hard lint-level ban from day one, not a documentation note.
A long-lived stream per tab costs server resources.Needs backpressure, idle eviction, and graceful degradation to plain request/response — and the degraded path has to be a first-class tested mode, not a fallback nobody runs.

Resident-set digests are a fingerprinting surface.A precise set of held template hashes is identifying. It has to be probabilistic, coarse-bucketed, and scoped to the origin — and it must be possible to disable entirely with the only cost being a fallback to html form.
Epochs can leak.Staged data that is never committed and never discarded is a memory leak with a plausible-looking cause. Epochs need explicit lifetimes, a bounded count, and eviction on navigation — and weft why has to show what is staged and how old it is.
Incremental server rendering may not pay for itself.The literature is clear that graph-structure changes are the hard case, and HTML rendering changes structure constantly. Memoisation costs hashing and storage. Keep it opt-in, measure per slot, and be prepared for the honest finding that it only wins for expensive structurally-stable regions.
Profile-guided planning can overfit.A profile from last month optimises for last month's users. Traffic shifts, a flag rolls out, a market launches, and the prebuild set is now wrong in a way nobody notices because the fallback path still works — just slower. Profiles need staleness warnings, and the generated plan needs to degrade visibly rather than silently.
The two-phase lifecycle is a real authoring tax.Splitting envelope from render is the correct design and it is still a second function to write and a concept to learn. If phase A ends up commonly needed, the ergonomics matter enormously — and if it is rarely needed, most people will meet it for the first time while debugging.
Deferred envelope effects are silently lossy.Attaching a cookie to the next request works beautifully until there is no next request. The type system can restrict this to idempotent effects, but "idempotent" is a judgement the author makes and can get wrong. Needs telemetry on drop rate, not just a type.
Profiles are production data.Navigation traces and per-route field metrics are behavioural data about real users. The profile artifact must be aggregate-only, checked in as thresholds rather than traces, and never carry anything that could identify a session.
