Weft by Example

The syntax, built up one level at a time — from a route that ships zero bytes of JavaScript to per-slot executors, staged epochs, and a delivery plan generated from a production profile. Nothing below level one is required to ship.

Seven levels Two files minimum No sigils · no 'use client'

Ground rules

Four decisions that shape everything else

01
Components are TSX. Delivery is a separate DSL.The component layer stays deliberately unremarkable — familiar to read, no new dialect to learn, and it works with the editors, linters, formatters, and codemods that already exist. The new syntax is reserved for the delivery plan, where there is nothing to be compatible with and everything to gain from being machine-checkable and machine-writable.
02
A fragment is the unit of everything.Composition, streaming, caching, code splitting, and delivery all use the same boundary. A fragment is a slot; a slot has a derived cache key, a negotiated wire form, an executor, and a budget. There is no second concept for "island" or "server island" or "region".
03
All request state flows through one typed context.This is what makes effect inference possible, and effect inference is what makes cache keys derived, cookies harmless, and boundaries automatic. Reaching around ctx is possible, loud, and local.
04
The plan lives in its own file because a machine writes it.If delivery decisions were decorators scattered through component code, a profile could not safely regenerate them. Keeping the plan separate is what makes profile-guided delivery possible at all.
app/ routes/ index.tsx ← a fragment. that is a whole route. cart/ route.tsx ← the route fragment cart-lines.tsx ← a child fragment = its own slot actions.ts ← intents route.plan.ts ← optional delivery plan shell.plan.ts ← optional app shell / regions flags.ts signals.ts weft.config.ts ← ports, adapters, plugins .weft/ profile.json ← generated by `weft profile` intents.d.ts ← generated. do not edit.
Level 0

A route

No plan, no config, no context. This ships zero bytes of JavaScript, renders at build time because it reads nothing, and is served from the CDN.

app/routes/index.tsx
export default function Home() {
  return (
    <main>
      <h1>Sindibad</h1>
      <p>Groceries, delivered.</p>
    </main>
  )
}

A plain function is a fragment with no effects. The compiler observes that it reads nothing, classifies it static, resolves it at build time, and writes a file. There is no getStaticProps, no export const prerender, no annotation — the classification is derived, and it changes the moment you read something.

Level 1

Reading things

The moment you need request state, take the context. Every read through it taints the fragment, and the taint set becomes the cache key.

app/routes/cart/route.tsx
import { fragment } from 'weft'
import { newCart } from '~/flags'
import { CartLines } from './cart-lines'

export default fragment(async (ctx) => {
  const currency = ctx.cookie('currency') ?? 'IQD'   // taints cookie:currency
  const layout   = await ctx.flag(newCart)             // taints flag:new-cart

  return (
    <section>
      <h2>Your cart</h2>
      <CartLines currency={currency} variant={layout} />
    </section>
  )
})
What the compiler wrote down, without being asked

reads = [cookie:currency, flag:new-cart] · class = SHARED — no identity was read, so this is CDN-cacheable · key = h(cart@a91f, currency, new-cart) · Vary: Cookie · flag axis new-cart registered, so the losing branch's chunks become unreachable rather than shipped.

Add ctx.user() and the class flips to PRIVATE, the key gains an identity component, and a .cache('public') declaration anywhere on this slot becomes a build error naming the read that caused it.

Level 2

Streaming, by composing

There is no <Suspense> and no <Await>. A fragment is the only streaming boundary, so if you want a hole, you compose a fragment. One rule, no second concept.

app/routes/cart/cart-lines.tsx
import { fragment } from 'weft'

export const CartLines = fragment<{ currency: string }>(async (ctx, props) => {
  const lines = await cart.lines(ctx.user(), props.currency)   // slow. that's fine.

  return <ul>{lines.map(l => <li key={l.sku}>{l.name} — {l.price}</li>)}</ul>
}, {
  placeholder: () => <ul aria-busy="true"><li></li><li></li></ul>
})

The parent does not wait. It emits its own markup with a declarative-shadow-DOM hole where CartLines goes, flushes immediately, and fills the hole out of order when the query resolves — with no JavaScript involved in the filling. The placeholder is part of the fragment because that is where it belongs; the parent should not have to know what its children are waiting for.

Consequence worth internalising

await inside a fragment blocks that fragment. It never blocks its parent and never blocks the response. So the way to fix a slow page is to move the slow thing into its own fragment, which is also the way to give it a cache key, a wire form, an executor, and a budget. The refactor that improves performance is the same refactor that improves structure.

Level 3

Interactivity

Signals make a subtree reactive. The compiler derives the island boundary from reactive reachability — which subtrees can actually change — and ships only those. No 'use client', no $ sigil, no directive of any kind.

app/routes/cart/quantity.tsx
import { fragment, signal } from 'weft'
import { addToCart } from './actions'

export const Quantity = fragment<{ sku: string; unit: number }>((ctx, p) => {
  const qty   = signal(1)                      // reactive → island
  const total = () => qty() * p.unit             // derived, tracked

  return (
    <form intent={addToCart} params={{ sku: p.sku, qty }}>
      <input type="number" value={qty()} onInput={e => qty(+e.target.value)} />
      <output>{total()}</output>
      <button>Add</button>
    </form>
  )
})

What ships to the browser: the wiring table entries for two bindings — output's text node and input's value — one event handler, and the intent id. Not the fragment. Not the framework's renderer for this subtree. Not p.unit, which was folded into the server-rendered bytes.

Intents — the client never names server code

app/routes/cart/actions.ts
import { intent } from 'weft'
import * as v from 'valibot'          // any Standard Schema library

export const addToCart = intent({
  params: v.object({ sku: v.string(), qty: v.pipe(v.number(), v.minValue(1)) }),
  capabilities: ['cart:write'],           // checked against the session

  async run(ctx, { sku, qty }) {
    await cart.add(ctx.user(), sku, qty)
    return ctx.refresh('cart-lines')      // single-flight: mutate + refresh, one trip
  }
})

The build emits an opaque id for this intent. The browser sends INTENT 7f3 {sku,qty} — an id and typed params, never a function reference, never a module path. The kernel validates the params against the generated schema, checks cart:write against the session, and only then runs. Renaming the export does not change the wire; changing the params schema does, and a stale client gets a clean rejection rather than a coerced value.

Level 4

The envelope, when you need it

Cookies, redirects, and status codes must be decided before the first byte leaves. So they live in a separate function with a separate context type — which makes the classic streaming bug impossible to write rather than caught at runtime.

app/routes/account/route.tsx
export default fragment({

  // phase A — nothing has been sent. envelope is open.
  // this is the ONLY thing between the request and the first flush,
  // so keep it cheap. `weft build` enforces a budget here.
  envelope(ctx) {
    const session = ctx.session.get()
    if (!session) return ctx.redirect('/login')     // a real 302
    ctx.session.rotateIfStale()                       // a real HttpOnly cookie
  },

  // phase B — streaming. `ctx` is RenderContext, which has no
  // redirect/cookie/status methods. the mistake cannot be typed.
  async render(ctx) {
    return <Profile user={ctx.user()} />
  }
})

Most of the time you should not write envelope() at all — the need is almost always an auth guard, and guards belong in the plan where they run in phase A by construction:

app/routes/account/route.plan.ts — the 90% case
guard(session.required, { redirect: '/login' })
Two escape hatches, both typed

ctx.envelope.deferrable(fn) is callable in phase B. The effect is queued onto the headers of the next request on the Warp connection — a real HTTP response, so HttpOnly and Secure work. Only for idempotent effects: token rotation yes, recording consent no. If there is no next request the effect is dropped, and the drop rate is reported.

ctx.envelope.inband(fn) emits a REDIRECT or COOKIE frame the client acts on. Cannot produce a real status code or an HttpOnly cookie. The type signature says so, and weft why flags every use.

Level 5

The plan

Everything so far works with no plan file at all — defaults come from the effect graph and, once you have one, the profile. The plan exists for the decisions you want to make deliberately, and for the ones a profile has made for you and checked in.

app/routes/cart/route.plan.ts
import { plan, when, every } from 'weft/plan'
import { newComposer } from '~/flags'
import { session } from '~/guards'

export default plan(({ slot, flag, device, gate, after, predict, guard }) => {

  guard(session.required, { redirect: '/login' })

  /* ── what arrives first ─────────────────────────────── */
  slot('header').static().critical()

  slot('cart-lines')
    .stream({ order: 'out-of-order', prio: 1 })
    .cache('60s', { swr: '10m', tags: ['cart'] })
    .form({ prefer: 'delta', fallback: 'data' })
    .refresh(every('30s'), { when: when.visible.and(when.focused) })

  /* ── what must not block anything ───────────────────── */
  slot('recommendations')
    .stream({ prio: 3 })
    .executor('pool:heavy')                    // off the request thread
    .budget({ cpu: '120ms', onExceed: 'placeholder' })
    .optional()                                // failure is invisible

  /* ── what loads later, or never ─────────────────────── */
  slot('editor')
    .island({ budget: '8kb' })                 // build fails if exceeded
    .load(when.visible.and(when.idle))
    .css('inline')

  /* ── the interactivity milestone the boot is ordered around ─ */
  gate('typeable', () => slot('composer').interactive(), { budget: '60ms' })
  after('typeable').load('analytics', 'history', 'models')

  /* ── conditional shape ─────────────────────────────── */
  flag(newComposer).then(() =>
    slot('composer').island().load(when.interaction('focus')))

  device.lowEnd.then(() => slot('recommendations').executor('client'))

  /* ── one prediction signal, three readiness layers ──── */
  predict(when.hover('a[href^="/checkout"]'), { delay: 80 })
    .speculate('prerender')      // browser Speculation Rules
    .discover()                  // PLAN extend — routes, chunks, css
    .warm({ epoch: 'next' })     // slot data, staged, unpainted
})

Two conditions that lie to you

when.idle cannot assume idle callbacks fire. requestIdleCallback is not Baseline — Safari ships it only behind a feature flag real users never enable — and scheduler.postTask is Chromium-only. It compiles to a ladder: postTask, then requestIdleCallback, then a timeout heuristic. A large share of iOS traffic gets the timeout, so anything gated on idle has to be genuinely optional.

prefers-reduced-data is Chromium-only and behind a flag. It is in the list above for completeness; treat it as decoration, not a signal you can act on.

You are not expected to write this by hand

weft profile reads production RUM and emits the plan — prebuild set, flush order, chunk packing, wire-form defaults, island load conditions, speculation eagerness. The generated file is checked in, so a delivery regression shows up as a plan diff in code review: someone adds a cookie read and the reviewer sees a slot move from shared to private.

Hand-written entries are marked and never overwritten. The generator only touches what it owns.

Reference

Every rendering and caching strategy, and what it actually is

There is no page-level rendering mode here, because the plan works per slot. So SSG, ISR, SWR, SSR, PPR, and CSR stop being framework features and become descriptions of configurations — combinations of what a fragment reads, which RenderPort serves it, and which executor runs it.

The industry names, translated
Name you knowWhat it is hereHow you get it
SSG / static A fragment whose effect set is empty .static() — or nothing at all, since it is the derived default. Resolved at build, written as a file, served by the CDN. The kernel is never invoked.
SSR (dynamic) A fragment that reads something request-scoped Automatic the moment you call ctx.cookie(), ctx.user(), or similar. Not a mode you select.
Streaming SSR Any fragment with async work The default. await blocks that fragment and nothing above it.
ISR Render once on miss, cache, serve from cache .cache('5m')
SWR Serve stale instantly, revalidate behind the response .cache('5m', { swr: '1h' }) — the revalidation runs through revalidateAfterResponse, which is waitUntil on Workers and a task queue on Node.
On-demand ISR Tag-based purge from anywhere .cache('1h', { tags: ['sku:{sku}'] }) then ctx.invalidate(['sku:1234']) from an intent, API route, webhook, or cron.
DPR / persistent Cache forever, purge deliberately .cache('∞', { tags: [...] }). Nothing expires; invalidation is the only path.
PPR Static shell plus dynamic holes Automatic. It is simply what the effect graph produces — nothing to enable, no Suspense boundary to place, no tree to audit.
CSR Render in the browser .executor('client')
Edge SSR A deployment choice, not a rendering mode topology plus which tier holds the executor. The fragment source is unchanged.
stale-if-error Serve the last good value when a render fails or blows its budget .budget({ cpu: '120ms', onExceed: 'stale' })

A page using six strategies at once

app/routes/product/[sku]/route.plan.ts
export default plan(({ slot }) => {

  slot('chrome')                                   // SSG
    .static()
    .critical()

  slot('product-core')                             // ISR + on-demand purge
    .cache('1h', { tags: ['sku:{sku}'] })
    .stream({ prio: 1 })

  slot('price')                                    // SWR — never make anyone wait
    .cache('30s', { swr: '10m' })
    .refresh(every('60s'), { when: when.visible })
    .form({ prefer: 'delta' })                      // refreshes cost ~100 bytes

  slot('reviews')                                  // heavy, off-thread, degrade to stale
    .cache('15m', { swr: '1h' })
    .executor('pool:heavy')
    .budget({ cpu: '150ms', onExceed: 'stale' })

  slot('cart')                                     // PRIVATE — reads ctx.user()
    .stream({ prio: 2, placeholder: 'skeleton' })   // no .cache(). it would be
                                                    // a build error anyway.

  slot('price-history')                            // CSR — below fold, chart lib
    .executor('client')
    .island({ budget: '14kb' })
    .load(when.visible)
})

Level 6

Ports, plugins, and the shell

One config file wires the swappable parts. Nothing here is a framework feature — caching, flags, sessions, storage, and execution are all port implementations, typically under a hundred lines each.

weft.config.ts
import { defineConfig, env } from 'weft'
import workers    from 'weft/adapter-workers'
import { memory, kv } from 'weft/store'
import { workerPool } from 'weft/executor'
import openfeature from 'weft/flags-openfeature'
import i18n from '@weft/i18n'

export default defineConfig({
  adapter:  workers(),
  topology: 'monolith',     // 'split-render' | 'edge-regional' | 'mesh'

  ports: {
    // an array IS the cache topology: L1 then L2.
    store:   [ memory({ max: '32mb' }), kv({ binding: 'CACHE' }) ],
    flags:   openfeature({ provider: statsig() }),
    session: cookieSession({ secret: env('SESSION_SECRET') }),
    executor: { 'pool:heavy': workerPool({ size: 4 }) },
    registry: fileRegistry('./regions.json'),
  },

  plugins: [ i18n({ locales: ['en', 'ar', 'ku'], dir: 'auto' }) ],
  profile: './.weft/profile.json',
})

Swap workers() for node() and the same build output runs on a container. Swap kv() for redis() and caching behaviour does not change, because the key came from the effect graph rather than from the store. Change topology and the framework splits across machines — the internal protocol is already the wire protocol, so there is no translation layer.

The in-memory tier, specified properly

L1 is where the wins are — sub-microsecond, no serialisation, no network. It is also the one tier you cannot reach from outside, which is the whole problem. So it needs a size limit, a TTL, and an answer for remote invalidation.

memory() — bytes, not entries
memory({
  max: '32mb',            // real byte accounting, including the tag index.
                            // entry counts are useless when values vary 100×.
  maxEntries: 20_000,      // optional second bound, for pathological cases

  ttl: '60s',              // default; per-slot .cache() overrides it
  staleTtl: '10m',          // keep serving stale while revalidating

  eviction: 'w-tinylfu',    // | 'lru' | 'lfu'
                            // w-tinylfu wins clearly on skewed web traffic;
                            // it is ~200 lines and we are building anyway.

  singleFlight: true,      // hold in-flight promises, not just values.
                            // dedupes concurrent identical renders in-process
                            // BEFORE reaching for a distributed lease. free win.

  coherence: 'tracking',    // ← the interesting one. see below.
})

Five ways to flush L1 from outside

'ttl' Bounded staleness only. No coordination at all. None — you wait it out Everywhere. The default.
'generation' L1 keys are prefixed with a generation counter read from L2 with a 1s TTL. Bump the counter and all of L1 is logically void, lazily. Coarse — all or nothing Everywhere, including Workers. One cheap L2 read per second.
'pubsub' Subscribe to a channel; drop entries matching invalidated tags. Per tag Node, Bun, Deno, containers. Needs a persistent connection.

Workers cannot do four of the five, and pretending otherwise would be dishonest

You cannot address an isolate. There is no handle for it, no way to enumerate them, thousands may exist, and they are created and evicted unpredictably. So no pub/sub subscription survives, and no tracking connection persists.

On Workers the honest configuration is ttl plus generation, with a short L1 TTL — single-digit seconds — because an isolate may live for minutes and you have no way to reach it. Your real shared cache there is KV or the Cache API at L2, and L1 is a request-coalescing layer more than a cache. Which is still worth having: singleFlight alone eliminates duplicate renders within an isolate.

Flags are built in, because the compiler needs them to be

This one is not a preference. Flag-axis partitioning and ahead-of-time permutation building both require statically enumerating the variant space — you cannot make a flag a partition of the module graph if you do not know its possible values at build time. A third-party provider SDK is an opaque function call, so it can tell you nothing. The first-party engine exists to make the architecture work.

app/flags.ts — declarative, so the compiler can read it
import { flag, rollout, rule } from 'weft/flags'

export const newCart = flag('new-cart', {
  variants: ['v1', 'v2'] as const,     // typed. this is the plan axis.
  default: 'v1',

  rules: [
    rule({ when: { tenant: 'acme' },      then: 'v2' }),
    rule({ when: { country: ['IQ', 'JO'] }, then: rollout({ v2: 10 }) }),
  ],

  // deterministic bucketing: hash(key + stableId). no round trip,
  // works at the edge, reproducible in tests and in CI.
  bucketBy: 'stableId',
  sticky: 'cookie',
})

What the built-in engine gives you that an adapter cannot:

  • Static variant enumeration → flag axes, graph partitioning, and profile-selected prebuild permutations. The losing branch's chunks are unreachable rather than shipped.
  • Edge evaluation with no network hop — rules are pure functions of resolved context, so the gateway decides before rendering and phase A stays near-zero.
  • The payload inlined into the first flush — the pattern the production teardown shows being hand-built with a Statsig snapshot. Flag names are hashed by default, for the same roadmap-leakage reason.
  • A kill switch that is one store read — force a variant globally without a deploy, backed by whatever StorePort you configured.
  • Exposure logging through TelemetryPort, which feeds the profile, which decides which permutations to prebuild. The loop closes.
  • Local overrides: weft flags set new-cart=v2.

A plugin declares its surface up front

plugins/i18n.ts
export default definePlugin({
  name: '@weft/i18n',
  after: ['@weft/session'], before: ['@weft/analytics'],   // a DAG, not integers

  reads:    ['cookie:locale', 'header:accept-language'],  // declared AND enforced
  provides: ['ctx.t', 'ctx.locale'],

  build: {
    transform(mod) { /* extract message catalogs */ },
    planAxis()     { return { locale: ['en', 'ar', 'ku'] } }  // new cache dimension
  },
  runtime: {
    onRequest(ctx)      { /* resolve locale; taints the fragment */ },
    onPlanResolve(plan) { /* swap the RTL stylesheet slot */ }
  }
})

A plugin that touches request state it did not declare throws in development. That single rule is what protects effect tracking — without it, one careless plugin silently makes every fragment uncacheable, which is exactly how caching dies in real codebases. A plugin with only build hooks provably ships zero runtime bytes.

The tension this creates, and how it resolves

If flags partition the module graph and the profile prunes cold permutations, does forcing a 0%-traffic variant on find nothing to run? No — because declaration and prebuilding are different things.

How public config reaches the browser

inlined once, then nothing — the resident-set mechanism again
first response    CONFIG gen=41 {api.url:"…", maps.key:"…", locales:[…]}
                  └ inlined into the first flush. no extra request.

later responses   client's RESIDENT frame says  cfg=41
                  → server sends nothing at all.

after a change    CONFIG gen=42 {api.url:"…"}
                  └ only changed keys. pushed on the open connection —
                    live clients update without a reload.

Worth contrasting with the build-time route: env.public('API_URL') is inlined into the bundle at build, which is marginally faster and requires a rebuild to change. config.public() is delivered at runtime, costs a few bytes on first flush, and is changeable from a ConfigMap. Both exist because the tradeoff is real; the runtime one is the better default.

Three enforcement layers, because a type alone is not enough

  • Type. Private values are branded and not Serializable, so they cannot be a fragment prop, a wire field, or an intent return.
  • Graph. Reading private config makes the module server-resident, transitively. A client chunk reaching it fails the build with the import chain.
  • Runtime. The serialiser refuses to emit anything carrying the private brand — because as any defeats a type, and someone eventually writes it. This is the layer that actually holds.

Why this is not just another router

Derived cacheability applies to JSON too. A handler that reads only path params is CDN-cacheable and the framework says so; one that touches a cookie is automatically private, and declaring it public is a build error naming the read. No API layer anywhere derives its own cacheability — that is why one-cookie-poisons-everything happens on the API side as well.

Everything else is shared. Same ports for store, flags, session, and telemetry. Same executors and budgets. Same tag invalidation, so an API mutation invalidates the fragments that render the same data. Same effect tracking, so the same guarantees hold on both sides of the app.

Level 9

Sharding across workers and servers

Decomposition is cheap here for one reason: the internal protocol is the wire protocol. A remote executor returns Warp frames, and the gateway forwards them into the client's stream — there is no translation layer to write, and no serialisation format to invent.

The one genuinely stateful piece — be honest about it

Everything above is stateless and replicates freely. Push invalidation is not. To send STALE to the right clients you need an index from cache tag to live connection, and live connections are state that has to live somewhere.

On Workers: a connection is held by a Durable Object (STREAMS.idFromName(sessionId)), and a second DO class shards the tag index by tag hash. Invalidation goes tag-DO → connection-DO ids → frames. On Kubernetes: connections live in gateway memory with a local tag map, and invalidation fans out over Redis pub/sub to every gateway — no sharding needed, because each gateway only indexes its own connections.

And if you do not want it: turn it off. Clients fall back to revalidating on focus or on their declared refresh interval. The entire push-invalidation tier is optional, and saying so is more useful than pretending it is free.

Deliberately refused

No HTTP server: the kernel takes a Web Request and returns a Response, per WinterTC, so it mounts inside Hono, Elysia, Express, or nothing at all. No compressor: CompressionStream and the CDN already exist. No validator, no parser, no bundler, no CSS engine, no test runner, no state manager, no CSS-in-JS.

One checkable commitment

The kernel ships zero runtime dependencies. Not "few" — zero. It imports only the WinterTC Minimum Common API, and every platform capability arrives as a port the application wires up.

Nitro demonstrated the value of this direction by cutting from 321 dependencies to fewer than 20 and reaching a sub-10 KB server bundle. Starting from zero is easier than getting there later, and it is a claim anyone can verify with one command rather than a promise about intentions.

Implementation

What the framework itself is written in

This is largely decided for us by one constraint: it has to run on Cloudflare Workers, which executes JavaScript and WebAssembly and nothing else. That rules out the tempting answer of "write the fast parts in Rust" for anything on the request path — but it does not rule it out for the toolchain, which runs on your machine.

Layer by layer, with the reason rather than the preference
LayerLanguageWhy, and why not the alternative
Client runtime TypeScript The budget is 4–6 KB and it needs direct DOM access. WebAssembly is the wrong tool twice over: a module plus its glue would blow the budget on its own, and every DOM touch has to cross back into JavaScript anyway. Compiles to tight, tree-shakeable JS.
Server kernel TypeScript Rust compiled to WASM would run on Workers, and would then make every port implementation an FFI exercise — which destroys the promise that a store adapter is under a hundred lines. It also counts against the 1-second startup budget. Users write fragments in TS; keeping the kernel in TS means no boundary crossing per render.
Ports and adapters TypeScript These are the contribution surface. They must be trivial to read, fork, and write against the WinterTC standard library. Anything else defeats the architecture.
Hot inner loops Rust → WASM, later and optional Only two pieces qualify: byte-segment assembly with escaping, and the Warp frame codec. Both take bytes and return bytes, so the FFI boundary is one copy each way rather than per-fragment. Ships behind a port with a JS fallback, and only if measurement justifies it — small payloads may lose more to boundary crossing than they gain.
Build toolchain Rust, by reuse Do not write a bundler. Rolldown for bundling, Oxc for parsing and transforming, Lightning CSS for styles — all Rust, all already fast, all in the same family.
Our compiler passes TypeScript on Oxc's AST Effect inference, island-boundary derivation, wiring-table generation, and template segmentation are AST work. Writing them as Rust plugins would be faster per file and would gut the contributor pool. Start in TS, port individual passes to Rust when the build's own profile says to — the same discipline applied everywhere else here. AST work parallelises across files, so the wall-clock cost is smaller than it sounds.
CLI and dev server TypeScript It has to load your weft.config.ts, which is TypeScript, and drive Vite's Environment API for the client, SSR, edge, and fragment environments.

Why not Go, or Zig, or a new language

Go compiles to WebAssembly with a runtime and a garbage collector attached, which is the wrong shape for something living inside a 128 MB isolate with a startup budget. Zig is a genuine alternative to Rust for the frame codec specifically — tiny binaries, clean WASM output — and loses on ecosystem alignment, since the toolchain we are reusing is Rust. A purpose-built language would spend the entire innovation budget on the part of this design that is not the point; the novelty is the delivery layer, not the syntax, and generated code is now a first-order concern.

One constraint on the plan DSL worth stating explicitly

The plan is TypeScript because it needs types — flags, slots, guards, and contracts are typed references, and a YAML or TOML plan would lose checking across those namespaces entirely. It also needs to be generated and rewritten by weft profile, which is far easier against a typed AST than a config format.

But it must be evaluable at build time with no runtime dependencies. A plan file cannot import your application code, cannot perform I/O, and cannot branch on anything unknowable at build time. This is why when combinators lower to a serialisable condition table instead of closures — the plan has to be shippable inside the stream as data. Think of it the way a Vite config is TypeScript but constrained: real types, no side effects.

Honest note

The one place I would reconsider

Keeping components in TSX is a pragmatic call, not an obviously correct one. A purpose-built template dialect — Marko's or Svelte's shape — would give the compiler more to work with: cleaner static-versus-dynamic segmentation for pre-encoded bytes, control flow that lowers to optimal code without inference, and simpler proofs that the html, data, and delta forms of a fragment are equivalent.

I chose TSX because the ecosystem cost of a new component dialect is enormous — editor support, linters, formatters, codemods, type-checking, and everyone having to learn it — and because Solid already demonstrates that a compiler plus signals over TSX reaches the right performance tier. Remix 3 trimmed its own domain-specific language for a related reason.

But if the equivalence proofs turn out to be fragile in practice, that is the signal to revisit. It would be the single largest change to this design, and it should be made on evidence from the differential-testing harness rather than on taste.
