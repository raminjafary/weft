Weft Field Notes

The complete survey behind the architecture proposal: what was searched, what was found, which numbers are trustworthy, and what each finding actually implies for the design. Including the parts we could not verify.

Method

How to read this

Every factual claim carries a source-quality marker, because a meaningful share of what turns up when searching "framework 2026" is search-optimised filler that recycles other people's numbers. Design decisions should not rest on those.

  • Primary — official documentation, changelogs, specifications, or a first-party engineering blog. Safe to design against.
  • Secondary — a named practitioner or a reputable technical publication summarising primary material. Trustworthy in substance; verify exact figures before quoting.
  • Unverified — aggregator or content-farm material. Directionally useful, numerically suspect. Flagged wherever it is the only source for a figure.

The survey covered sixteen areas: rendering architectures, reactivity, hypermedia, micro-frontends, server runtimes, build tooling, routing, caching, feature flags, browser transport primitives, off-thread rendering, server-side surgical updates, data prefetching, incremental computation, profile-guided optimisation, and server-driven UI security — plus one production case study. Each finding below ends with its consequence for the design rather than being left as trivia.

Area one

Rendering architectures

Streaming SSR with out-of-order holes is a solved problem Secondary

React 18's Suspense SSR architecture, Solid's renderToStream, and Marko all implement placeholder-then-fill streaming. Marko's variant is the most complete: it separates component code that never needs to reach the client, streams out-of-order content, and inserts finished sections into the same response via script insertion rather than waiting. Ryan Carniato has stated directly that Solid's streaming SSR came from studying Marko at eBay.

ImplicationDo not treat streaming as a differentiator. It is table stakes, and the differentiator is what the hole boundary is — component boundary today, addressable slot in our design — and whether the stream survives past the document.

Resumability is architecturally sound and commercially stalled Unverified

Qwik is reported at roughly 672 detected sites against Astro's 7,885 and Remix's 2,209. The figures come from an aggregator and the absolute numbers should not be quoted, but the ratio is consistent with every other signal about Qwik's traction. The criticisms are consistent across sources: the mental shift, the $ sigil syntax, and ecosystem workarounds.

Technically, Qwik's primitive is the QRL — a lazy reference to a function — and it serialises not just state but handler locations and component boundaries, which requires serialising closures. Qwik's own documentation calls closure serialisation the key property enabling resumability. A criticism found in the surveyed material is notable: other partial-hydration solutions serialise less because they know statically what is server-only.

ImplicationThe goal is right, the mechanism is the problem, and the lesson is that architecture alone does not win adoption. Resumability via a compiled wiring table plus signal values avoids closure serialisation entirely — and the component syntax must stay unremarkable.

Islands are mainstream, and their costs are now visible Primary

Astro 7 shipped 22 June 2026. Its model distinguishes client islands, hydrated independently, from server islands, which render dynamic content on the server separately from the page. The 2026 consensus is that islands are the default for content-heavy sites.

ImplicationTwo limits to design past: island boundaries are hand-annotated by the author rather than derived, and each server island costs its own HTTP request. Compiler-derived boundaries plus one multiplexed stream address both.

Signals won reactivity; the wire format for shipping them did not get standardised Primary

The TC39 Signals proposal sits at Stage 1, deliberately: the stated plan is significant early prototyping and framework integration before advancing. It is backed by maintainers from Angular, Vue, Solid, Preact, Ember, Qwik, and MobX. Polyfills exist and the API is not final.

ImplicationBuild the client graph on the proposal's shape so the runtime can be shed later, but expect no standard for serialising a signal graph server-to-client. That format is ours to define, and it is what makes the data wire form possible.

The 2025–26 mood is consolidation, not new paradigms Secondary

Carniato characterises the period as core refinement rather than architectural breakthrough, and identifies three directions: AI-first design — Remix 3 explicitly reducing domain-specific language so models generate it more easily — isomorphic-first architecture, where TanStack Start, SvelteKit, and SolidStart converge on out-of-order streaming plus server functions plus granular optimistic UI plus single-flight mutations, and async-first primitives. He also observes that AI code generation has gutted the value of curated opinion layers such as Redwood and create-t3-app.

ImplicationTwo direct constraints. Keep the component layer conventional and generable — invent syntax only for the delivery plan, where there is nothing to be compatible with. And do not position this as an opinion layer; position it as a primitive nobody has.

Area two

Hypermedia and server-driven UI

Datastar is the closest existing thing to the protocol we want Primary

Roughly 11 KB, unifying Alpine-style reactivity with htmx-style server interaction. Its signals are JSON objects declared on the client and synchronised with the server over HTTP requests and SSE. It accepts both text/html and text/event-stream, so a handler can return markup or stream events. The stated philosophy is that the backend drives state and is the source of truth.

ImplicationStudy the wire design closely; it has already validated bidirectional signals over SSE with fragment merging. What it lacks is everything around it: a compiler, a type system, a module graph, an island model, a build. That is the whole opportunity — the protocol idea is proven, the engineering around it is absent.

Mobile server-driven UI solved render authority years ago Secondary

The practices found: sign layouts with Ed25519 verified against a pinned public key bundle, include expiring timestamps against replay, validate against schemas at the edge and on-device with hard caps on depth, breadth, and total size, allowlist URL schemes and hosts, rate-limit layout requests and bind them to session and device identity with token rotation, and forbid certain component types — PIN entry is the cited example — from ever being server-driven. Critically: components must be registered on the client, so the server cannot conjure new functionality at runtime.

ImplicationThis is the model for the render-intent catalogue. The web's server-function designs let the client reference server code; a registered-capability allowlist inverts that. Adopting a discipline proven in a more adversarial environment is cheap and defensible.

Area three

Micro-frontends and fragments

Cloudflare's fragment architecture is the reference for edge composition Primary

An application is a tree of fragments, each deployed as a Worker, collaborating to server-side render one response: the browser requests a root fragment, which talks to child fragments. Fragment piercing allows incrementally converting the valuable parts of a legacy UI in isolation from the surrounding shell.

ImplicationThe composition model is validated in production. The reported weaknesses — young tooling, painful debugging, thin observability, platform lock-in — are precisely what a framework-level protocol with a causal explain tool would fix.

Web Fragments buys isolation with an iframe per fragment Primary

Fragments live in shadow roots for style isolation and execute their JavaScript in a separate context backed by a hidden iframe, while sharing the document, navigation, and history. A fragment gateway middleware routes browser requests to the right fragment endpoint, keeping everything on one origin. Removing a <web-fragment> element destroys its iframe context and releases its memory. In beta, in production at Cloudflare.

ImplicationThe gateway concept transfers directly. The iframe-per-fragment cost does not: with content-addressed templates, per-fragment CSP, and typed signal contracts, isolation can be structural rather than paid for at runtime. Their memory-lifecycle discipline is worth copying regardless.

"Rendering as a service" is common practice and quietly insecure Secondary

The documented pattern is extracting SSR into its own Node service to which a monolith delegates, passing component names and the data they need. Reported cost: rendering a complex application to an HTML string takes 10 ms to 100 ms in the worst case as a single synchronous task.

ImplicationTwo findings for the price of one. Tier separation is established practice worth making declarative — and passing component names across a service boundary is exactly the vulnerability the intent catalogue closes. An opaque intent ID with a validated param schema costs nothing extra.

Area four

Server runtime and portability

WinterTC gave portability an actual specification Primary

WinterCG shut down in January 2025 and was replaced by Ecma TC55, "WinterTC". The Minimum Common Web API's first edition tracks the 2025 snapshot and was adopted as an Ecma standard in December 2025. Work in progress includes a test suite, a Sockets API for unified TCP and TLS, and a CLI API for environment variables, arguments, and working directory.

Implication"Platform-agnostic" can now be a conformance claim rather than an aspiration. The kernel targets the Minimum Common API and nothing else; the eventual test suite becomes our portability CI.

Nitro 3 is the prior art for ports and adapters, and it is only half the idea Primary

Nitro 3 beta reports roughly 280k weekly downloads since the October 2025 alpha, a minimal server bundle under 10 KB with the standard preset, and dependencies cut from 321 to fewer than 20. Presets are first-party and maintained, so when a platform API changes the preset absorbs it. SWR and ISR are configured declaratively — swr: true or swr: 3600, and an isr property — backed by a caching layer and a storage abstraction. h3 supplies web and plain adapters with Web Streams across Node, Bun, Deno, Workers, and Vercel.

ImplicationAdopt the preset model wholesale; it is the best-executed deployment abstraction in the ecosystem and the sub-10 KB figure sets our kernel budget. But note what is adapter-shaped there and what is not: platform and storage are ports, while rendering strategy is still a config keyword handled by framework internals. That is the half nobody has done.

Workers' 2026 limits are what make fine-grained fragments viable Primary

The February 2026 changelog removed the 1,000-subrequest cap: paid Workers now default to 10,000 per invocation and can be configured up to 10 million, while free-plan Workers remain at 50 external subrequests plus 1,000 to Cloudflare services. Startup time rose from 400 ms to 1 second in October 2025. CPU time is 10 ms per request on free and 30 seconds by default on paid, configurable to 300,000 ms. Memory is 128 MB per isolate on both plans. waitUntil extends execution up to 30 seconds after the response is sent or the client disconnects.

ImplicationEvery one of these is a design input. The subrequest change is what makes per-fragment remote rendering plausible at all. The 128 MB ceiling forces a bounded L1 cache and streaming rather than buffering. waitUntil is the SWR revalidation primitive. And the 1-second startup budget is why the kernel must not import Node shims.

Service bindings make splitting cheap, and the docs are honest that it is not free Primary

Cloudflare's RPC system lets one Worker call another with, in their words, zero overhead or added latency — by default both Workers run on the same thread of the same server, so calls stay in the same execution thread and decomposition introduces no network latency. The same material notes the counterweight: each call still adds latency even if sub-millisecond, and each additional Worker adds deployment, versioning, and cognitive overhead. Use RPC when the target exposes functions, fetch-forwarding when it processes requests.

ImplicationThis is the enabling primitive for tier decomposition, and the stated caveat is why the monolith topology stays the default. Warp-over-fetch-forwarding is the portable tier boundary; RPC is an optimisation on top.

Storage consistency classes differ enough to belong in the type system Primary

KV offers sub-5 ms reads from 300+ locations but is eventually consistent with writes propagating within 60 seconds, and each key can be written at most once per second — exceeding that errors. D1 is SQLite-backed and queryable. R2 is object storage without egress fees. Durable Objects provide scalable compute with consistent storage.

ImplicationKV is a good L2 for shell buffers and flag payloads and a bad one for anything write-heavy, and that distinction should not live in a documentation footnote. Putting a consistency field on StorePort turns a production incident into a build error. Durable Objects are the natural stampede-lease holder.

Area five

Build tooling

Vite's Environment API already models what we need Primary

Vite 6 formalised environments, letting framework authors create as many as their production topology requires. Three communication levels are offered so frameworks can write runtime-agnostic code, with the recommendation to implement the most flexible available. Low-level configuration lets runtime providers ship environments with correct defaults, and environments can spawn processes or threads to run modules in something closer to the production runtime during development. Rolldown, the Rust Rollup replacement, is Rollup-plugin-compatible and reported at 10–30× faster, bringing dev and prod bundling logic closer together.

ImplicationDo not build a bundler. Client, SSR, edge, and fragment environments map onto this directly, and the ability to run modules in a closer-to-production runtime during dev is what makes per-slot executors testable locally. This is the largest single piece of work we get to skip.

Area six

Routing, caching, flags

Fog of War is proven, and applied to exactly one thing Primary

React Router's lazy route discovery ships only the manifest entries the current page needs, expanding the route tree as the user navigates, via a /__manifest endpoint and patchRoutesOnNavigation. The headline number is Shopify's: a 1,300-route manifest over 10 MB uncompressed dropped to 3 routes and 1.9 KB for the initial homepage.

ImplicationThe mechanism and its payoff are established. The generalisation is untouched: the same treatment for CSS, island chunks, flag payloads, and data schemas. Also note the practitioner-reported friction with client-side useNavigate — lazy discovery must not make ordinary navigation surprising.

Per-unit caching exists but the keys are hand-written and the runtime is restricted Primary

Next.js use cache marks a route, component, or function cacheable; functions using it must be async; cacheLife sets duration and cacheTag enables on-demand invalidation via revalidateTag and revalidatePath. Critically, the directive requires the Node.js runtime and the Edge runtime rejects it outright — the documented workaround is falling back to fetch with revalidate options.

ImplicationTwo independent weaknesses to beat. Hand-declared keys drift from what the code actually reads, which is why derived keys are the strongest idea in our design. And a caching primitive unavailable on the edge runtime is a direct consequence of caching being a framework internal rather than a port.

Flag handling is either a runtime branch or a combinatorial build Primary

The Flags SDK turns each flag into a callable function, works with any provider through adapters, and keeps pages static via precompute: middleware evaluates flags and encodes the result into the URL by rewrite, and generatePermutations builds every combination at build time for CDN distribution. It is described as working well for marketing-page experimentation and for serving multiple static shells for partial prerendering. Separately, a widely-shared 2026 article frames the core problem as one cookie wrecking an entire Next.js app's caching.

ImplicationThe precompute pattern is a workaround for a missing primitive, and its own framing admits the boundary: static shells. Neither approach makes a flag a partition of the module graph, so the losing branch's code still ships. That is the gap — and the cookie article is direct evidence that derived cache keys address a problem people already feel acutely.

No prior art found for flag-aware bundling Unverified

A targeted search for feature-flag-aware compilation, per-flag bundle splitting, and build-time flag variants returned only C, C++, and Go compiler documentation about dead-code elimination and build tags. The search engine itself noted the absence of web-specific material.

ImplicationA negative result, and a useful one. Go's build tags are the closest conceptual relative — conditional compilation controlled by declared axes. Treat this as an open area, and verify by reading bundler source directly rather than trusting a search.

Area seven

Browser and transport primitives that changed the calculus

Out-of-order streaming can now need zero JavaScript Primary

Declarative Shadow DOM turns a <template> with shadowrootmode into its parent's shadow root during parsing. The attribute was renamed from shadowroot specifically to support streaming, and the shadow root attaches on the opening tag rather than the closing one, so content inside can render as it arrives. Slots within the shadow root can receive streamed content, achieving out-of-order streaming without JavaScript replacing anything. Support: Chrome and Edge 111+, Firefox 123+, Safari 16.4+.

ImplicationThis is a significant find. The entire out-of-order hole mechanism can be markup, which means holes fill before our runtime loads, or even if it never loads. It removes JavaScript from the critical path for the mechanism that historically required it most.

Compression Dictionary Transport is the byte-level half of our idea, already shipped Primary

RFC 9842, in Chrome and Edge since version 130 in late 2024, Firefox in progress. A previously fetched resource serves as a compression dictionary so a later response transfers roughly as a delta plus references. Cloudflare published a detailed preview and confirmed beta availability on 17 April 2026, implementing it at the edge without origin-side work. Google has applied it to Search.

ImplicationThis turns the resident-template idea from speculation into engineering. The two layers compose: the resident-set digest removes semantic redundancy by choosing a cheaper wire form, dictionaries remove byte redundancy from whatever form is sent. Content-addressed template versions are already natural dictionary candidates — the design gets this nearly for free.

Speculation Rules plus cross-document view transitions make MPA navigation competitive Primary

Speculation Rules is explicitly designed for multi-page sites rather than SPAs, and Chrome 144 in January 2026 added a mode that fetches HTML and begins rendering and subresource loading but pauses JavaScript at the first blocking script — preloading CSS, images, and fonts without triggering script side effects like analytics. Cross-document view transitions opt in from CSS via @view-transition and are supported in Chromium and Safari 18.2+, with Firefox in progress. Combining them means transitioning between two already-rendered documents.

ImplicationThe MPA-versus-SPA choice should be a plan-level decision rather than a framework identity. Our design should emit speculation rules from the plan's own predictive-discovery signals — it already knows which routes are likely next, which is exactly the input the API wants. The script-paused prerender mode is particularly well matched to a design whose first flush needs no JavaScript.

Edge Side Includes has been quietly modernised Secondary

ESI designates page elements as independently processable fragments assembled at the CDN edge, with fragment-level caching and per-fragment TTLs. Fastly has published an ESI library for JavaScript Compute, available on npm.

ImplicationWorth respecting as a twenty-year-old precedent for exactly the composition model being proposed. Its per-fragment TTL model is a subset of derived cache keys, and its main historical failure — no type safety, no shared reactivity across fragments — is what we are adding.

Area eight

Off-thread rendering: everyone does it, no framework offers it

The pattern is universal and entirely outside the frameworks Secondary

Published accounts from Yelp, Expedia, Tinkoff, and Wix converge on one architecture: a main thread that receives requests and a pool of rendering workers. The main thread can fast-fail based on average render time and queue depth; a worker handles one request at a time, so blocking its event loop is acceptable. A Node worker thread is a full V8 isolate with its own heap and event loop, roughly 10 MB of memory overhead and startup in the tens of milliseconds. Piscina exists as the general-purpose pool implementation. Wix reports cutting thousands of SSR pods and the associated cost by applying multi-threading. Inngest's assessment — worker threads are problematic but work well for this — is worth heeding.

ImplicationThe strongest kind of gap: a problem every serious operator has solved identically, outside the tool that causes it. Making render locus a per-slot declaration with a CPU budget and a defined degradation path converts institutional folklore into a framework primitive. The fast-fail-on-queue-depth heuristic should be built into the scheduler port, not left to users.

Area nine

Surgical updates: the strongest prior art we found

Phoenix LiveView solved minimal recompute and minimal wire diff with one mechanism Primary

LiveView's template engine splits a template into static and dynamic parts. The first render sends both; every subsequent render sends only the dynamic parts, and only those whose backing assigns actually changed, tracked through a __changed__ map. The wire format is binary and described as efficient on the server as well as over the wire. The documentation is explicit that one design solves two problems at once: not executing the dynamic parts that did not change, and not sending them. LiveView 1.0 shipped and the engine is now at 1.1.x.

ImplicationThis is the standard to beat, and it should be benchmarked against directly rather than hand-waved past. The static/dynamic split validates the pre-encoded-segments approach independently. What it cannot do is the opening: it requires a stateful process per connection holding the previous render, which rules out serverless and edge runtimes, forces sticky sessions, scales memory with concurrent users, and means a diff is computed per connection and never shared. Ten thousand users seeing the same price change means ten thousand identical diffs.

Blazor Server reaches the same destination more expensively Primary

A component re-render re-executes BuildRenderTree, produces a new render tree, diffs it against the previous one, batches the minimal DOM operations, serialises them and sends them over SignalR. The documented performance advice is about avoiding unnecessary renders, because even with efficient diffing those renders still consume CPU and memory — particularly on the server.

ImplicationRecompute-then-diff is strictly worse than not recomputing, which is why LiveView's approach is the better model. Blazor also confirms the statefulness constraint is inherent to server-held render state, not an Elixir quirk. Both point to the same conclusion: move the render state to the client and the server can be stateless.

Route-level data prefetching is thoroughly covered Primary

TanStack Router preloads by intent using hover and touchstart on Link, with a 50 ms default delay configurable via defaultPreloadDelay, and by viewport using IntersectionObserver. It has a built-in SWR cache for route loaders, and preloaded matches are held in memory with unused preload data evicted after 30 seconds by default.

ImplicationDo not claim prefetch-on-intent as novel; it is mature and well-designed. Three things remain open and all three matter: granularity is the route rather than the slot with its own key, there is one wire form so a client already holding the template still receives markup, and the preload lands in the same cache the live view reads — which is exactly why prefetching can disturb the current view. Epochs, slot-level keys, and form negotiation address those three specifically.

Incremental computation is a mature field that never reached HTML rendering Secondary

Self-adjusting computation builds a dynamic dependence graph recording control and data dependencies between sub-computations, then uses graph algorithms to recompute a minimal subset when inputs change; memoisation and adaptive computation are described as duals whose combination yields the technique. Adapton made it composable and demand-driven. Salsa is the Rust framework built on memoising function results, and is what makes rust-analyzer viable. The literature is explicit about the limitation: changes to the structure of the computation graph are difficult for these systems to process.

ImplicationThe theory is available and the production precedent exists. The stated weakness is the design constraint: HTML rendering changes graph structure constantly through conditionals, list reordering, and mount/unmount. So incremental recompute must be opt-in per slot, and honestly it will only pay where the region is expensive and structurally stable. Claiming otherwise would be overselling.

Area ten

Profile-guided everything, except delivery

PGO is standard practice with well-documented gains Primary

Profile-guided optimisation, also called feedback-driven optimisation, improves large-application performance by improving code locality and instruction-cache utilisation, with reported gains in the 15–30% range. The dominant drivers are function inlining and basic-block reordering. Post-link binary optimisers such as BOLT and Propeller consume AutoFDO profiles to refine layout further, adding 5–15% depending on workload. Go's PGO design document specifies the AutoFDO-style workflow directly: collect profiles from production, then supply them when building the updated binary.

ImplicationThe workflow is proven and the analogy to delivery planning is structural rather than rhetorical. Basic-block reordering maps onto flush order and chunk packing; inlining maps onto folding a near-universal island into the first flush; tiered compilation maps onto prebuilding the head of the traffic distribution and rendering the tail. Adopt the vocabulary deliberately — it makes the design legible to anyone who has shipped a PGO'd binary.

Guess.js already tried the web version, narrowly, in 2018 Primary

During the build, the Guess plugin fetched a report from Google Analytics, built a model — Markov chains, neural networks, or TensorFlow are all cited — and added a small runtime to the main bundle. At runtime it predicted likely next pages and prefetched their bundles, taking the top-N paths at each step. Early benchmarks reported around 20% better perceived page-load performance. It launched as alpha at Google I/O 2018.

ImplicationCredit this properly; it is the direct ancestor. It also shows the ceiling of the narrow version: prefetching alone, one decision, and the project is dormant. The generalisation — a profile that decides prebuild sets, flush order, chunk packing, wire-form defaults, island load conditions, compile hints, and speculation eagerness — is only possible if all those decisions live in one artifact, which is precisely what a delivery plan is and what Guess.js had no equivalent of.

The browser now accepts compile hints, and tells you it cannot advise you where Primary

Chrome 136 ships explicit compile hints: a magic comment at the top of a JavaScript file instructs V8 to parse and compile everything after it eagerly, off the main thread, often overlapping network load — instead of compiling on the main thread at first call. Experiments on popular pages improved 17 of 20, averaging a 630 ms reduction in foreground parse and compile time. File granularity only for now, with per-function selection stated as a long-term goal. The explicit caution is to use it sparingly, because over-compiling costs time and memory.

Implication"Use sparingly" is a profile question with no profile available. A delivery profile knows which chunks are executed on essentially every load, which makes hint emission a derived decision rather than a guess. This is a concrete, shipped, measurable win that falls directly out of having production data at build time.

The RUM-to-build loop runs the wrong way Secondary

The 2026 monitoring landscape is mature — Datadog, Grafana, Dynatrace, OpenObserve — and Datadog ships build plugins that integrate with JavaScript bundlers. What those plugins do is upload source maps and deobfuscation data: artifacts pushed to the monitoring service. Nothing found pulls production profiles back into build-time delivery decisions.

ImplicationA clean, checkable asymmetry, and the tidiest statement of the gap in this entire survey. The instrumentation already exists on both ends; the missing piece is an artifact worth optimising against. That is the argument for making the delivery plan a first-class file rather than behaviour scattered across link props and dynamic imports.

Area eleven

The envelope problem, and how every framework handles it

Late response headers are universally forbidden rather than solved Primary

Next.js documentation states that setting cookies is not supported during Server Component rendering, and gives the reason directly: streaming responses require headers to be sent before components finish rendering, so Set-Cookie after render has begun is impossible. The prescribed alternatives are a Server Function, a Route Handler, or middleware. SvelteKit's setHeaders must be called before resolve, and setting the same header twice raises an error — the reported case being Cache-Control already set from a root layout. Remix and React Router avoid the problem by running loaders to completion before rendering starts, which is correct and forfeits early flush.

ImplicationThree mature frameworks, three variations on "you cannot, do it in a different phase." The constraint is HTTP, not a bug, so the design goal is not to defeat it: shrink what it blocks, make the mistake type-impossible rather than runtime-guarded, provide a real second channel for late effects, and enumerate precisely what is irreducibly lost. Notably, Vary and Cache-Control — the most common late-header need — become derived rather than discovered once cache keys come from effects, so that case disappears entirely.

103 Early Hints is shipped, standardised, and unused by frameworks Primary

RFC 8297 defines a status code that sits between the request and the final response, letting a server nominate resources to preload before the real response is ready. Chrome, Safari, and Cloudflare have implementations, and Cloudflare exposes it in Workers directly. It is restricted to HTTP/2 and HTTP/3; Firefox's HTTP/1.1 implementation is not enabled by default. Cloudflare's own flow sends cached early hints immediately while forwarding the request to the origin in parallel.

ImplicationThis is the most valuable single find of the later research. The pressure to flush early is mostly about subresource discovery, and Early Hints delivers that without sealing the envelope — which means the two-phase lifecycle costs far less TTFB than it appears to. No framework surveyed emits 103 systematically from its own knowledge of the critical path, and we would already have that knowledge in the plan.

Orchestration is a solved category with two unsolved edges Primary

single-spa's root config is described as the backbone: an independent container devoid of business logic that registers applications via registerApplication with a name, a promise, and an activeWhen predicate, then drives bootstrap, mount, and unmount across framework boundaries. Its documented hazard is that incorrect lifecycle handling causes memory leaks, UI conflicts, and unexpected behaviour — correctness is the application author's burden. Module Federation covers dependencies: singleton: true with strictVersion: true throws when multiple versions of a shared package appear, requiredVersion sets semver scopes, and mismatches otherwise produce duplicate React instances that break hooks and context. Type safety across remotes exists through a TypeScript plugin generating declaration files, with CI contract tests recommended — and the observation that teams skipping them hear about version skew from users.

ImplicationDo not claim typed cross-boundary contracts as novel; they exist. The two genuine edges are narrower. First, contracts are verified in CI against published types rather than against what production is serving at the moment of deploy. Second, the runtime failure mode is an exception or a silently duplicated dependency, never a declared degraded fallback. Both are addressable by making the shell a plan — regions get budgets, fallbacks, and optionality from machinery that already exists for slots.

The opt-out cliff is documented by the framework that has it Primary

In a non-PPR Next.js route, any dynamic function call — cookies(), headers(), searchParams — anywhere in the route tree opts the entire route out of static rendering; the documented example is a personalised banner making a whole page dynamic. Partial Prerendering changes this: dynamic calls isolated inside Suspense boundaries no longer opt the whole route in, and the static shell outside those boundaries is prerendered and cached at the edge. The stated requirement is to identify every dynamic call in the tree and confirm it sits inside a boundary.

ImplicationThe clearest possible confirmation of the cliff problem, from primary docs. The fix exists but the boundary is hand-drawn and must be audited and remembered. Deriving the boundary from effect tracking removes both the audit and the failure mode — which is a modest-sounding difference that eliminates an entire class of production surprise.

Case study

A production streaming-SSR app, torn down

The app is chatgpt.com, and that is incidental — it is cited only because a detailed public teardown of its delivery layer exists, which is rare. It is an ordinary React Router 7 + Vite web app; the subject matter is irrelevant and no part of this proposal involves machine learning. What makes it the single best evidence for where the missing primitives are is that it operates at extreme scale on an unremarkable stack, with everything that makes it fast living above the framework. The conclusion this drives

Not one item in the second half of that table is a framework feature anywhere. Boot sequencing around a named milestone, per-route CSS splitting, server-computed per-user prefetch, flags that control delivery rather than UI, inlined flag payloads, hashed flag names, and custom RUM marks for framework-invisible milestones — all hand-built, all rebuilt independently at every company operating at this scale.

A missing primitive is exactly this: work that competent teams keep re-implementing identically because the layer that should own it does not exist.

Area twelve

Browser baseline audit

Run against every platform dependency the design introduced. Two findings forced corrections to the proposal.

Declarative Shadow DOM reaches Baseline Widely Available today Primary

Chrome and Edge 111, Safari 16.4 (March 2023), Firefox 123 (20 February 2024). The web-features explorer gives shadowrootmode an expected Widely Available date of 2026-08-20 — the 30-month threshold falls on the day of this survey. WebKit has its own implementation writeup. Separately, Chromium tracks "streaming declarative shadow DOM" as a distinct feature entry.

ImplicationThe feature is safe to depend on; the streaming semantics are the open question. A separate Chromium feature entry for streaming behaviour, when the attribute itself is standardised and shipped everywhere, is a signal that incremental-parse behaviour may differ by engine. The "zero JavaScript out-of-order streaming" claim was corrected to "zero JS where incremental parsing works, ~1 KB filler script where it does not" — and that script must be built and tested regardless, not treated as a contingency.

Streaming request bodies are Chromium-only, so Warp's uplink had to change Primary

duplex: 'half' must be set on any request with a stream body, and it means the request completes before the response is available. True duplex: 'full' is a reserved future addition that no browser implements. Streaming uploads require HTTP/2. Separately, Safari does not support for await…of over a response stream — proposed for Interop 2026 — though getReader() works.

ImplicationDescribing Warp as a duplex channel was wrong and would have made the core Chromium-only. Corrected to a logical channel with three transport bindings: streamed response down plus discrete POSTs up (the Baseline default), WebSocket for true duplex (also Baseline), and WebTransport later. The frame vocabulary is identical across all three, which is precisely the value of having defined a frame vocabulary rather than an API.

requestIdleCallback is not Baseline Primary

Safari does not support it by default in any stable version; WebKit ships it behind a feature flag on macOS and iOS that production users will not enable. MDN states plainly that it is not Baseline. scheduler.postTask is Chromium-only and still experimental. The recommended pattern is feature detection with a setTimeout fallback.

Implicationwhen.idle — used liberally in the plan examples — cannot assume idle callbacks fire. It compiles to a ladder: scheduler.postTask, then requestIdleCallback, then a timeout heuristic. Worth noting that a large fraction of iOS traffic gets the timeout path, so anything gated on idle needs to be genuinely optional.

View Transitions: same-document is Baseline, cross-document is not Primary

Same-document view transitions reached Baseline Newly Available with Chrome 111, Safari 18, and Firefox 133+; the ViewTransition interface reached Baseline in October 2025, and Firefox 144 supports document.startViewTransition and view-transition-name. Cross-document navigation transitions are not in Firefox stable, with support anticipated during 2026.

ImplicationGood news for epochs: committing a staged epoch behind a same-document transition is Baseline, so the flagship interaction is safe everywhere. The MPA-mode polish is progressive enhancement, which is the correct place for it.

Three accelerators are Chromium-exclusive Primary

Speculation Rules is Chromium-only. Compression Dictionary Transport is Chrome and Edge 130+, Firefox in progress, no Safari. V8 explicit compile hints are Chrome 136+ and V8-specific by definition. 103 Early Hints is better placed — Chrome, Safari, and the Cloudflare edge — with Firefox's HTTP/1.1 implementation not enabled by default, and it is HTTP/2-and-above only. prefers-reduced-data is Chromium and flagged.

ImplicationNone of these may sit on a critical path, and all of them cost nothing when absent — which is the right shape. The real hazard is benchmarking: a test suite that runs only in Chrome would overstate this design specifically because two of its most attractive features are Chromium-only. Publish per-engine numbers or publish none.
The architectural payoff

Capability variance is not a special case in this design. The RESIDENT frame already carries client capabilities alongside RTT and CPU class, and form selection is already a per-request negotiation — so a browser lacking a capability is never offered the form that needs it.

No feature-detection sprawl, no polyfill layer, no parallel code path. Browser fragmentation turns out to be the same problem as network and cache variance, and it gets the same mechanism. This is the most convincing practical argument for negotiation as an architecture rather than a feature.

Area thirteen

Reactivity, isolation, variants, and concurrency

The virtual DOM question is closed, and so is the update-performance race Secondary

Vue 3.6 reached release candidate on 18 July 2026 with Vapor Mode feature-complete, RC.2 following on 22 July, and stable expected in autumn. Vapor compiles templates to imperative DOM operations, shrinking bundles 20–50% for Vapor-only components, with benchmarks reported as landing in the same range as Solid.js and Svelte 5 — up to 97% faster renders in extreme cases, 100,000 components in roughly 100 ms. Solid never had a VDOM; Svelte 5 rebuilt reactivity around runes.

ImplicationThe most important negative finding in the survey. Three independent implementations converging on the same performance band is strong evidence that fine-grained-signals-to-direct-DOM is at the floor. Claiming to beat them on isolated update benchmarks would not be credible, and a design marketed on that axis is marketing a tie. Publish those numbers to prove parity; differentiate elsewhere.

Hydration is O(n); resumability is O(1) — and the spectrum is documented Secondary

The clearest available framing: React executes components on hydration and on interaction; SolidJS executes them on hydration only; Qwik does not hydrate and so executes neither. Hydration requires every component in the tree to execute before any event handler is live, which produces the "visible but unresponsive" gap between FCP and TTI. Resumability recovers state without re-executing components, making the JavaScript cost constant in application size rather than linear.

ImplicationThis is where the real headroom is, and it is large. A wiring table that adopts existing DOM by position gives the O(1) property without Qwik's closure serialisation. Two corollaries worth measuring: for server-rendered content the DOM is created by the native HTML parser rather than a JS creation path, and a content-addressed wiring table can be cached across page loads — no framework currently caches its hydration work at all.

SvelteKit's server-only rule is the right standard Primary

Server-only modules are declared by a .server.js suffix or by living in $lib/server, and SvelteKit refuses to let client code import them. The documented reasoning is the part that matters: even when public-facing code uses only the non-secret exports, the secret code can still end up in the JavaScript the browser downloads, so the import chain itself is considered unsafe. import type is the sanctioned escape.

ImplicationAdopt the standard — reject on the chain, not on apparent usage — and fix its two gaps. It protects only modules someone named correctly, and it says nothing about data leaking, since a properly server-resident module can still serialise a password hash into the page. Derived transitive residency closes the first; the wire schema doubling as a serialisation allowlist closes the second.

Layered overrides are proven; typed multi-dimensional ones are not Primary

Nuxt Layers let a project extend a base app from a monorepo, git repository, or npm package; directories are scanned and merged with the consuming project always winning, which makes layers safe to consume. The documented white-label use case is exactly the target: a base layer holding logic, data-fetching patterns, and default UI, with each tenant layer overriding only a branded header, a layout, and config. Priority matters when extending several layers. Separately, React Native resolves .ios and .android file extensions by platform, and Android generalises this to many qualifiers with a documented precedence table that must be followed in order.

ImplicationBoth mechanisms work and both are worth copying. Three things are missing: overrides are not type-checked against the base, so drift is silent until a customer finds it; layers are a linear chain rather than an N-dimensional typed tuple; and neither knows anything about caching. The third is the important one — making a variant dimension taint the fragment means cross-tenant cache leakage becomes structurally impossible, and that is among the most persistent bugs in real multi-tenant systems. Also worth deciding deliberately: Nuxt Layers are build-time only and SaaS multi-tenancy is runtime-only, while the same source needs to support both.

Parallel middleware is standard in distributed systems and absent from web frameworks Secondary

Web frameworks model middleware as a sequential chain of responsibility: authentication, logging, parsing, error handling, each passing the request down, with an error short-circuiting the rest. The DAG alternative models inter-item dependencies as read-write, write-read, and write-write relationships in an adjacency matrix; because results are futures, independent branches execute concurrently and — in the literature's own words — the parallelism is a consequence of the declared dependency structure, requiring no explicit concurrency code from developers.

ImplicationWe already have the declarations. reads and provides give exactly that adjacency relation, so dependency edges are inferred rather than hand-written and disjoint items run concurrently by default. The design consequence is the filter-versus-enricher split: short-circuiting requires sequence, enriching does not, and most of what people write as middleware is an enricher. It also extends to fragment evaluation — render as a DAG rather than a root-to-leaf walk — which is safe here only because render is provably read-only.

The consequence for our headline claim

Half the comparative performance numbers circulating for 2026 frameworks come from sources that do not state their hardware, payload, or concurrency. "Faster than any framework" cannot rest on beating those figures — they are not solid enough to beat.

Which is why the benchmark harness is phase zero. Publish the methodology and the workloads, make it runnable by third parties, and include tuned React Router 7 and SolidStart as the baselines. If the pre-encoded-shell approach does not win reproducibly, that is worth discovering in week two rather than year two.

Gaps in the research

What we did not establish

Stated plainly, because a survey that only reports what it found is not trustworthy. Each of these needs primary verification before it becomes load-bearing.

Whether flag-aware bundling truly has no prior art.The search returned nothing web-specific, but absence of search results is not absence of implementations. Verify by reading Rolldown, Rspack, and Turbopack source for conditional-graph support, and check whether any experimentation platform ships a bundler plugin that partitions rather than branches.
Whether streaming Declarative Shadow DOM behaves identically across engines.Now the highest-priority unknown in the whole survey. The attribute is Baseline as of today, but Chromium tracks streaming behaviour as its own feature entry, which suggests the incremental-parse semantics are less uniform than the support matrix implies. Test in Chromium, Gecko, and WebKit in week one: does content inside the template render as it arrives, and do slot assignments apply incrementally? The answer determines whether the filler script is a fallback or the main path.
Whether the ~1 KB filler script is actually enough.Asserted, not measured. Script-insertion hole-filling is what Marko and React already do, so the technique is proven, but our version also has to handle slot reassignment and out-of-order arrival. If it turns out to be 4 KB, the zero-JS story weakens materially and the content-site positioning changes.
Real-world Compression Dictionary Transport behaviour at our granularity.Google applied it to Search and Cloudflare offers it at the edge, but no source describes using per-template dictionaries at the granularity we propose. Dictionary count, eviction behaviour, and the cost of registering many small dictionaries are all unknown.
Marko 6's exact current state.Search returned fragmentary release notes and a Tags API preview rather than a clear picture of what shipped. Marko is the most architecturally relevant prior art in this entire survey and deserves a proper read of its source and compiler output, not a search summary.
Whether resumability without closure serialisation is actually sufficient.The claim is that a compiled wiring table plus signal values covers every case closures cover. That is a strong claim, and it is the load-bearing assumption of our client design. It needs a prototype against genuinely hard cases — event handlers closing over loop variables, derived state across island boundaries, conditional subtrees.
What the actual per-request cost of form negotiation is.Choosing a form requires a resident-set lookup and a size estimate per slot. At high slot counts that could plausibly cost more than it saves for cheap fragments. It needs measuring, and the answer may be that negotiation applies only above a size threshold.
Whether stateless delta computation actually beats LiveView's stateful version.The claim rests on base-render recovery from cache being cheap and on delta sharing across users being common. Both are plausible and neither is measured. If cache-miss rates on base recovery are high, the fast path rarely engages and the whole mechanism is dead weight. This is the single most important thing to prototype, and it should be benchmarked against a real LiveView app rather than an argument.
How often deltas are genuinely shareable in practice.The ten-thousand-users-one-delta argument assumes many clients transition between the same pair of content-addressed states. For public shared data that is likely; for anything personalised the pairs may be nearly unique, making the shared-delta cache useless. The answer probably differs per slot, which suggests it should be a measured, per-slot decision rather than a global claim.
Whether epochs are comprehensible to developers.Staged generations with atomic commit are a genuinely new mental model, and the whole design already asks a lot. It may need to be invisible by default — prefetch stages automatically, navigation commits automatically — with the explicit API reserved for the cases that need it. Worth testing on people before committing to a public surface.
How often late envelope effects actually occur in real applications.The entire two-phase design is justified by the claim that envelope work is cheap and rare while data fetching is expensive and common. That is intuitive and unmeasured. If a meaningful share of routes genuinely need a cookie written from a late slot, the design needs more than deferral and in-band frames. Worth auditing a few real codebases before committing.
Whether 103 Early Hints survives real CDN paths intact.It is HTTP/2-and-above only and passes through proxies, CDNs, and load balancers that may or may not forward it. Cloudflare supports it explicitly; other CDNs and self-hosted setups are unverified. Since the envelope design leans on it to recover TTFB, its real-world hit rate needs measuring rather than assuming.
Whether deploy-time contract verification is operationally acceptable.Refusing a deploy because a remote is serving an incompatible contract is correct and it also means one team can block another's release. That is a governance question as much as a technical one, and the answer may need to be a warning by default with enforcement opt-in per region.
Whether Guess.js's dormancy has a cause we would inherit.It may have stalled for reasons unrelated to the idea — maintainer time, the Google Analytics dependency, webpack coupling. Or it may have stalled because build-time analytics integration is operationally painful in ways that would equally afflict a profile-guided plan. This is worth finding out from the project's history before designing the profile pipeline.
